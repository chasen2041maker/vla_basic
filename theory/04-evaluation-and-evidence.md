# 04｜车没撞，为什么还不能说策略更好了？

材料补充：2026-09-27。本篇不改变当前课题，不提供第二个驾驶 runner。已有代码入口是实践仓库的 [demo.py](https://github.com/chasen2041maker/highwayenv-learning/blob/main/demo.py)；历史日志和测试参考是本仓库 [run_episode.py](../experiments/highway_driving/run_episode.py) 与 [test_episode.py](../experiments/highway_driving/tests/test_episode.py)。解释历史工具时基准为 `07195834977114e5fdffcf62358ea9ab93534612`，不把它当作实践 demo 的配置。

## 先看一个真实问题

把减速阈值从 40 米改到 50 米，新一局没有碰撞。可能是改动有效，也可能是这局前车更少、更快，或者程序提前停止。没有同条件对照，不能把幸运的交通当成算法收益。

评测位于“算法/控制执行之后的证据链”，负责回答某个版本在什么条件下表现如何，不负责替策略规避碰撞。指标本身也可能有 bug：把时间用尽算成安全成功，或遗漏提前结束的失败，都能做出漂亮但错误的报告。

## 从一局日志到公平比较

一次比较先固定环境版本、完整配置、场景定义、初始条件、交通行为规则、时限与随机种子列表。基线和修改版都跑同一份列表，按场景配对，而不是分别挑最好看的几局。相同 seed 只有在相关代码、依赖与随机数消费方式稳定时才有复现意义，不能跨版本无条件保证相同交通。

开发场景用于发现问题和调参，另留一组没用来调阈值的检查场景。看过并据之修改后，这组已参与开发；下一轮应明确记录，不继续称它是完全未见测试。

每回合至少记录：代码/策略/config/环境版本、场景及 seed、实际步数与仿真时间、碰撞、驶离道路、环境终止、时间上限、脚本上限、进展和必要运动量。碰撞导致短回合，不能通过删除短回合或只比较幸存者获得虚假改进。

这是一份后续实践接口要求，不是说当前 demo 已记录全部字段。真实批量执行与归档应在实践工程按当前任务逐步实现。

## 指标先回答自己的问题

| 问题 | 一个可用起点 | 容易犯的错 |
| --- | --- | --- |
| 出现了多少失败？ | 同一套预定义场景下，有碰撞回合数 / 有效评测回合数；另报失败类型和暴露时间 | 把一段 rollout 中每个碰撞帧都当独立事故；排除失败回合 |
| 是否完成任务？ | 预先定义的路线进度或目标到达，保留超时和中止原因 | 只要进程退出 0 就算任务成功 |
| 是否僵住？ | 进展、低速停滞时间，结合场景要求 | 为零碰撞永远不动，却宣布更好 |
| 是否平顺？ | 在统一采样时刻计算实际加速度、jerk 或控制变化，声明测量方式 | 将归一化动作当作真实加速度；不同采样间隔直接比较 |
| 是否符合适用条件？ | 分场景报告覆盖、失败与缺失；说明未测的交通/天气/道路 | 用直路简化仿真外推到城市实车 |

离散速度近似加速度可写为 `a=(v_next-v)/dt`，单位 m/s²；jerk 是相邻加速度差再除以 dt。必须使用真实 dt，考虑采样噪声与滤波，不把这里的有限差分当高精度传感器测量。

奖励由环境设计，可能混合速度、车道、碰撞等项；它可以辅助比较，但不能代替上述可解释指标。相关接口与结束标记见 [Gymnasium Env API](https://gymnasium.farama.org/api/env/)，读取于 2026-09-27。

## 零次碰撞提供了多强的证据？

假设每回合是相互独立、同分布的 Bernoulli 试验，失败概率为 p，n 次都没失败的概率是 `(1-p)^n`。令这个概率为 0.05，可得零失败时的单侧 95% 精确上界 `p_upper=1-0.05^(1/n)`。

它是特定抽样模型下的区间构造，不是“真实失败率有 95% 概率低于这个数”的保证。重复同一 deterministic seed 100 次不等于 100 个独立场景；人工挑选的回归集也未必代表道路分布。此时下面的数只能用于理解样本量，不能作为真实道路安全论证。

把下面代码作为局部公式例子保存为临时文件 `zero_failure.py`，在该目录运行 `python zero_failure.py`。VS Code 用 Ctrl+P 定位你刚保存的文件；本仓库没有同名评测入口。

```python
import math


def zero_failure_upper(n: int, alpha: float = 0.05) -> float:
    if isinstance(n, bool) or not isinstance(n, int) or n < 1:
        raise ValueError("n 必须是正整数")
    if not math.isfinite(alpha) or not 0 < alpha < 1:
        raise ValueError("alpha 必须在 (0, 1) 内")
    return -math.expm1(math.log(alpha) / n)


if __name__ == "__main__":
    for n in (20, 100):
        print(f"n={n}, upper={zero_failure_upper(n):.4%}")
    assert zero_failure_upper(20) > zero_failure_upper(100) > 0
    try:
        zero_failure_upper(0)
    except ValueError:
        print("invalid n rejected")
    else:
        raise AssertionError("未拒绝零样本")
```

预期打印约 `13.9108%`、`2.9513%`，并拒绝零样本。先预测样本数变大时上界如何变化，再运行；这些是数学例子，不是你的驾驶成绩，也不是推荐仅测 20 或 100 局就足够。

## 旧测试证明什么，没证明什么

旧 `test_episode.py` 检查了真实环境的一步、观察契约、同 seed 复现、SLOWER 改变运动、脚本/环境时限区分、trace 连续和非空白回放。`test_logic.py` 则检查参数和结束原因分类。它们比只检查图片存在更有价值。

但结束分类函数的假输入测试不等于强制构造了真实碰撞或驶离道路。现有这两份测试也不是跟车策略评测、训练质量或视觉验证。后续应在实践工程增加可控失败场景、指标正反例与修复后的回归；不要为“补测试”改坏历史教学基线。

## 开放环和闭环别混在一起

开放环：在记录的数据上预测，与给定标签或规则比较；预测通常不改变后续输入。它适合调数据和模型，但可能看不到执行误差累积。

交互闭环：自己的动作改变后续状态和观察，其他参与者是否响应也要由环境协议说明。HighwayEnv 的交互练习属于简化状态仿真，不因此成为真实视觉闭环。

中间还有非交互 rollout、日志回放和伪仿真。报告必须说明是否连续推进、是否与交通参与者交互、是否重规划以及控制器来源，不能都简称“闭环通过”。一个修改可能降低离线轨迹误差却恶化执行，这是需要解释的实验结果而不是删掉的异常。
