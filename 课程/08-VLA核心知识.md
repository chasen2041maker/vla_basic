## 1. 为什么要学

阶段 05 的 ACT 是「一个任务一个模型」。换个任务要重新采数据、重新训练。而且它不理解语言——你没法告诉它「这次抓蓝色的」。

VLA（Vision-Language-Action）想解决这个：**一个模型，用自然语言指定任务，输出动作。**

在整个具身系统里，VLA 占的是「小脑」这一层，和阶段 05 的 ACT 同一个位置，只是多了语言输入和预训练带来的语义先验。它的上面是阶段 04 的 LLM 规划层，下面是阶段 07 的安全过滤与硬件执行。

这是当前具身领域最活跃的方向，也是最容易被夸大的方向。**这个阶段最重要的产出不是跑通推理，是亲手测出它的能力边界。** 第 5 节的四个实验比前面所有代码加起来更值得投入时间——尤其是「给它一个无意义指令，它照样输出一个动作」这个观察，它直接决定了阶段 08 的整个设计。

## 3. 核心概念

### 3.1 VLA 的输入与输出

一句话：**拿一个视觉语言模型（VLM）当骨干，把输出头从「预测文本 token」改成「预测动作」。**

```
输入：图像（一路或多路相机）+ 文本指令（"pick up the red block"）
        │
        ▼
   VLM 骨干（视觉编码器 + 语言模型）
        │
        ▼
   action head（离散 token 或连续输出）
        │
        ▼
输出：动作（关节角 / 末端位姿增量 / 夹爪开合）
```

**注意输出侧和阶段 05 完全同构。** 那 7 个数字的语义问题（绝对还是增量、什么单位、夹爪的 0 是开还是关）在这里一字不变地存在，而且更容易搞错——因为动作定义来自你没参与采集的预训练数据集。阶段 05 第 3.3 节那张表，在这里要重新对着 checkpoint 的元数据填一遍。

### 3.2 为什么用 VLM 当骨干

VLM 在互联网规模的图文数据上预训练过，已经知道「红色」「杯子」「左边」这些概念之间的关系。

- ACT 从零学，你的演示数据必须覆盖所有情况
- VLA 借用预训练的语义知识，理论上能泛化到没见过的物体名称和指令措辞

这个思路和 LLM 微调是同一个套路：拿预训练模型，换个任务头，用少量领域数据微调。

**代价有三个，都是结构性的：**

1. **参数量大。** 7B 级别的模型，推理延迟从 ACT 的几毫秒变成几十到上百毫秒。这直接影响能不能闭环（见 3.8 节）
2. **数据需求大。** ACT 50 条能看到效果，VLA 微调通常需要几百条——因为你要教的不只是动作，还有「这句话对应这个动作」的映射
3. **语义先验不等于物理能力。** 模型知道「红色方块」是什么，不代表它知道以什么姿态能抓稳它。这两件事在预训练数据里的覆盖程度差异巨大

### 3.3 action head：离散 vs 连续

VLM 的输出头本来是预测词表上的概率分布。要输出动作，有两条路。**这是 VLA 的核心设计问题，也是理解这个领域演进逻辑的关键。**

**路线一：离散化成 token。**

把每个动作维度的连续值分成 N 个 bin（典型 N=256），每个 bin 映射到词表里一个 token。动作就变成了「文本」，可以直接复用 VLM 的自回归生成，不需要新架构。

```python
"""动作的离散化与反离散化。

这是离散路线的完整机制，代码量很小但有两个容易忽略的细节：
分位数归一化，以及量化误差不可恢复。

理解量化误差很重要——256 个 bin 听起来很多，但如果动作
范围是 ±0.1 米，每个 bin 就是 0.78 毫米，而抓取精度要求
可能正好在这个量级。
"""

import numpy as np


class ActionTokenizer:
    """把连续动作离散化成 token id，以及反向解码。

    分位数归一化是关键细节：不用简单的 min-max，而是用
    训练数据的 1% 和 99% 分位数作为范围边界。这样极端的
    离群动作不会把整个范围拉宽，导致常规动作全挤在中间几个 bin 里。
    （和阶段 05 第 3.5 节的 ActionStats 是同一个理由。）
    """

    def __init__(
        self,
        action_low: np.ndarray,
        action_high: np.ndarray,
        num_bins: int = 256,
        vocab_offset: int = 31744,
    ):
        self.action_low = action_low
        self.action_high = action_high
        self.num_bins = num_bins
        # 动作 token 占用词表末尾一段，避免和真实文本 token 冲突
        self.vocab_offset = vocab_offset

    def encode(self, action: np.ndarray) -> np.ndarray:
        """连续动作 -> token id 数组。"""
        # 归一化到 [0, 1]
        normalized = (action - self.action_low) / (self.action_high - self.action_low)
        normalized = np.clip(normalized, 0.0, 1.0)
        # 量化到 bin 索引
        bins = (normalized * (self.num_bins - 1)).round().astype(int)
        return bins + self.vocab_offset

    def decode(self, token_ids: np.ndarray) -> np.ndarray:
        """token id -> 连续动作。

        注意这里的量化误差是不可恢复的：encode 再 decode
        不等于原值。误差上界是 (high - low) / (num_bins - 1) / 2。
        """
        bins = np.clip(token_ids - self.vocab_offset, 0, self.num_bins - 1)
        normalized = bins / (self.num_bins - 1)
        return normalized * (self.action_high - self.action_low) + self.action_low

    def quantization_error_bound(self) -> np.ndarray:
        """返回每个动作维度的最大量化误差，单位和动作相同。

        动手算一下这个值，和你的任务精度要求对比。
        如果量化误差已经超过精度要求，离散化方案就不适用——
        这不是调参能解决的，是表示能力的硬上限。
        """
        return (self.action_high - self.action_low) / (self.num_bins - 1) / 2.0
```

**必做：** 用你阶段 05 的数据算一下 `quantization_error_bound()`，和抓取需要的精度对比。这会让你直观理解离散化方案的局限。

**路线二：连续输出。**

不离散化，用 flow matching 或扩散模型直接生成连续动作向量。优点：没有量化误差、天然支持动作分块、多模态表达能力强。缺点：需要额外的动作专家网络，架构更复杂，不能直接复用 VLM 的自回归解码路径。

这是当前的趋势方向。理解这个区别，你就理解了 VLA 从「动作当文本」到「独立动作专家」的主要演进逻辑。

### 3.4 action chunk

和阶段 05 的动作分块是同一件事，但在 VLA 上有一个额外的动机：**推理太慢，必须靠 chunk 摊薄延迟。**

```
单次推理 100ms，控制频率 30Hz（每步 33ms）
不分块：根本跑不动
chunk_size = 20：一次推理换 20 步动作，平均每步 5ms
```

所以在 VLA 里 chunk 不只是缓解分布偏移的技巧，是延迟预算的必需品。代价还是那个：chunk 内部开环执行，这段时间里策略完全不看反馈。**chunk 越大，你在闭环性上牺牲得越多。** 这个权衡在 3.8 节展开。

### 3.5 动作归一化：VLA 里最高频的失败原因

阶段 05 讲过归一化的机制。VLA 里它变成头号 bug 源，原因是**统计量不是你算的**。

预训练权重自带一份或多份动作统计量，通常按数据集命名（比如 OpenVLA 的 `unnorm_key`）。选错的后果：

| 情况 | 现象 |
|---|---|
| 用了另一个数据集的统计量 | 动作方向大致对，幅度差几倍到十倍 |
| 微调后仍用预训练统计量 | 同上，且系统性偏移 |
| 完全忘了反归一化 | 动作幅度是归一化空间的量级，几乎不动或直接冲限位 |

**三条规则：**

1. **微调时必须用你自己数据的统计量重算。** 你的动作分布和预训练数据不同，这是最常见的失败原因
2. **统计量的 key 名要写进部署代码的启动日志。** 让它可见，而不是藏在一个默认参数里
3. **每次换 checkpoint 都重新确认。** 同一个仓库的两个 checkpoint 可能用不同的 key

这是阶段 05 实验 3（用错的统计量）在真实场景里的样子。如果你在那里做过那个实验，这里会省下好几个小时。

### 3.6 language conditioning：语言是怎么进去的

语言指令进入模型的方式决定了它的作用强度。三种典型做法：

| 方式 | 机制 | 语言的影响力 |
|---|---|---|
| **prompt 拼接** | 指令作为文本 token 拼在图像 token 前后，一起过语言模型 | 强，但也最容易被视觉信号盖过 |
| **FiLM / 条件归一化** | 语言编码成向量，调制视觉特征的缩放和偏移 | 中等，作用位置明确 |
| **cross-attention** | 动作 query 对语言 token 做交叉注意力 | 中等到强，可解释性较好 |

**关键认知：语言输入存在但不代表它起作用。**

一个在单一任务数据上微调的 VLA，完全可以学会忽略语言——因为训练数据里语言和视觉是完全相关的（每次说「抓红块」时画面里也只有红块），模型走视觉这条捷径损失更低。**这时它表现得像一个 ACT，只是多花了 100 倍的算力。**

第 5 节的实验 1（语言敏感性）就是用来检测这件事的。这不是理论担忧，是很容易发生的实际情况。

### 3.7 多任务数据与 cross-embodiment

**多任务数据。** VLA 的优势要在多任务上才体现。单任务微调时 ACT 通常赢，因为它专精。数据组织上要注意：

- 每条轨迹必须有语言标注，且标注要有区分度（「抓红块」/「抓蓝块」，不是全都标「抓东西」）
- 任务之间的数据量要大致平衡，否则模型会偏向多数任务
- 语言标注的措辞要有变化，否则模型学的是「这个字符串」而不是「这个语义」

**cross-embodiment（跨本体）。** 一个 VLA 在 7 自由度机械臂上训练，能不能用在 6 自由度的低成本臂上？

**基本上不能，除非专门处理。** 原因：关节数量不同、关节限位和几何尺寸不同、相机位置和视角不同、夹爪形态不同。

三种处理方案：

**方案一：统一动作空间。** 不用关节角度，用末端位姿增量（Δx, Δy, Δz, Δrotation, 夹爪）。这个表示对不同机械臂通用，具体怎么实现由各自的 IK 负责。代价是引入 IK 的无解和跳解问题（阶段 05 第 3.3 节）。

**方案二：大规模混合数据训练。** 在聚合了多种机器人的数据集上训练，模型见过多种本体，泛化更好。

**方案三：本体适配层。** 主干模型输出抽象动作，每个本体有自己的小适配网络。

**对你的实际意义：下载的通用 VLA 权重不能直接在你的机械臂上用。** 需要在你自己采的数据上微调。很多人忽略这一点，然后困惑为什么零样本效果极差。

### 3.8 inference latency 与 closed-loop deployment

这一节是 VLA 和 ACT 最实质的工程差异。

**闭环的定义：** 每一步动作都基于最新观测。开环：一次决策管很多步。

VLA 的推理延迟（几十到上百毫秒）使得完全闭环不可行，实际部署总是某种程度的开环：

```
理想（闭环）：观测 → 推理 → 一步动作 → 观测 → ...
现实（分块开环）：观测 → 推理 → k 步动作（这期间不看观测）→ 观测 → ...
```

**延迟预算怎么算：**

```
控制频率 30Hz → 每步 33ms
其中包含：图像采集 + 预处理 + 推理 + 后处理 + 通信下发
如果推理单独就要 100ms，那么 chunk_size 至少要 100/33 ≈ 4
留余量的话取 10-20
```

**必须自己测的三个数：**

1. 单次前向的纯推理时间（不含数据搬运）
2. 端到端一次决策的时间（含图像采集、预处理、通信）
3. 上面两个数的差——这个差通常大得让人意外，图像采集和 USB 通信可能占大头

**为什么闭环性重要：** chunk 内开环的这段时间里，如果物体被碰动了、抓取滑脱了、有人把东西拿走了，策略不知道。它会继续执行一段基于过期观测的动作。**这正是阶段 08 要处理的问题的物理来源。**

### 3.9 fine-tuning 与 domain adaptation

全量微调 7B 需要多卡。LoRA 在单卡上就能做。

```python
"""VLA 的 LoRA 微调配置要点。

如果你做过 LLM 的 LoRA/QLoRA 微调，这部分不新鲜。
重点是下面三个 VLA 特有的注意事项，它们不在 LLM 微调的经验里。
"""

from peft import LoraConfig, get_peft_model

lora_config = LoraConfig(
    r=32,
    lora_alpha=64,
    lora_dropout=0.05,
    # 只对语言模型部分加 LoRA，视觉骨干通常冻结
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    task_type="CAUSAL_LM",
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
```

**三个 VLA 特有注意点：**

**1. 动作归一化统计量必须重算**（3.5 节）。这是头号失败原因，重复说一次不算多。

**2. 视觉骨干冻不冻。** 冻结省显存且不容易过拟合。但如果你的场景和预训练数据视觉差异很大（工业场景 vs 厨房），解冻视觉骨干的最后几层通常有帮助。这是 domain adaptation 里最有性价比的一个旋钮。

**3. 数据量需求比 ACT 大。** 几百条起。而且要有语言标注的多样性（3.7 节）。

**domain adaptation 的一般思路，按性价比排序：**

| 手段 | 针对的差异 | 成本 |
|---|---|---|
| 目标域数据微调 | 全部 | 采数据的成本，但最有效 |
| 图像增强（色彩、模糊、裁剪） | 视觉外观 | 几乎为零 |
| 解冻视觉骨干末几层 | 视觉分布差异大 | 显存 |
| 相机位置对齐到预训练设置 | 视角差异 | 只是摆放的功夫，常被忽略 |

最后一条经常被漏掉：**把你的相机摆到接近预训练数据集的视角，比任何算法手段都便宜。**

### 3.10 评估方法

阶段 05 的评估纪律（附随机化范围、至少 50 次、分等级、记录失败模式、固定种子）全部适用。VLA 多两个必须单独测的维度。

**维度一：指令跟随准确率。** 和成功率是两个不同的东西：

```
成功率：任务完成了吗
指令跟随准确率：完成的是我说的那个任务吗
```

场景里有红块和蓝块，你说「抓红块」，它抓了蓝块并成功放到目标位置——成功率可能被记为 1，但指令跟随是失败的。**必须分开统计**，否则你无法区分「模型学会了动作」和「模型学会了听话」。

**维度二：语言泛化。** 用训练时没出现的措辞、同义词、以及组合（「把红块放到蓝块左边」）。这才是 VLA 相对 ACT 的真正卖点，也是最容易虚高的地方。

**必须和 ACT 做同数据量对比。** 预期结果：数据量少时 ACT 会赢，因为它专精单任务。VLA 的优势要在多任务和语言泛化上才体现。**如果你的 VLA 微调效果比 ACT 差不少，那是正常的，不是你做错了。** 提前知道这一点能省下几天的自我怀疑。

### 3.11 VLA 与 LLM 规划层的分工

你现在有两个「智能」组件：阶段 04 的 LLM 规划器和这里的 VLA。

```
用户：「把桌上的东西收拾干净」
        │
        ▼
LLM 规划器（阶段 04）
  - 理解模糊指令，问清「收拾到哪里」
  - 拆解成技能序列
  - 跟踪世界状态，处理失败重规划
  - 决定什么时候需要人介入
        │  下发原子技能："pick up the red block"
        ▼
VLA（本阶段）
  - 把这一句话 + 当前图像变成动作
  - 只管这一个动作，不管全局
        │
        ▼
     机器人
```

**为什么不让 VLA 直接做长任务：**

- 没有长期记忆和状态跟踪
- 不会问问题，指令模糊时只能瞎猜
- 不会判断「这件事做不到」，任何输入都输出动作
- 没有失败识别能力，抓空了也会继续往下走

**为什么不让 LLM 直接输出动作：** 慢（秒级）且不精确（没有视觉伺服能力）。

这个分工是当前的主流架构，也是你的切入点所在——**你的能力在上面那一层，而那一层现在做得普遍很粗糙。**

## 4. 最小实验

**先做纯推理，不训练。** 目标是建立「图像 + 文本进，动作出」的直观，并测出延迟。

安装和显存要求见 `动态资料/2026-VLA模型与工具生态.md`。

```python
"""VLA 推理最小示例（以 OpenVLA 接口为例）。

这段代码的目的只有两个：拿到一个 7 维动作，以及测出延迟。
其他什么都不做。
"""

import time

import numpy as np
import torch
from PIL import Image
from transformers import AutoModelForVision2Seq, AutoProcessor

MODEL_ID = "openvla/openvla-7b"

processor = AutoProcessor.from_pretrained(MODEL_ID, trust_remote_code=True)
model = AutoModelForVision2Seq.from_pretrained(
    MODEL_ID,
    torch_dtype=torch.bfloat16,
    low_cpu_mem_usage=True,
    trust_remote_code=True,
).to("cuda")


def predict_action(
    image: Image.Image,
    instruction: str,
    unnorm_key: str = "bridge_orig",
) -> np.ndarray:
    """预测一个 7 维动作：(dx, dy, dz, droll, dpitch, dyaw, gripper)。

    注意这个默认输出是「末端位姿增量」而不是绝对关节角——
    对照阶段 05 第 3.3 节的表确认一遍，不要凭印象。

    unnorm_key 指定用哪个数据集的动作统计量做反归一化。
    这个参数选错会导致动作幅度完全不对：用 A 数据集的统计量
    去解码在 B 数据集上微调的模型，动作可能大十倍。
    这是新手最常见的错误之一（3.5 节）。
    """
    prompt = f"In: What action should the robot take to {instruction}?\nOut:"
    inputs = processor(prompt, image).to("cuda", dtype=torch.bfloat16)
    return model.predict_action(**inputs, unnorm_key=unnorm_key, do_sample=False)


def measure_latency(image: Image.Image, instruction: str, n: int = 20) -> dict:
    """测量推理延迟。

    必须先跑几次预热——第一次调用包含 CUDA kernel 编译和
    显存分配，可能比稳态慢一个数量级。用第一次的数字去算
    延迟预算会得到完全错误的结论。

    返回的 p50 和 p95 都要看：控制循环的可行性由 p95 决定，
    因为偶尔的长尾会导致丢帧。
    """
    for _ in range(3):
        predict_action(image, instruction)
    torch.cuda.synchronize()

    timings: list[float] = []
    for _ in range(n):
        start = time.perf_counter()
        predict_action(image, instruction)
        torch.cuda.synchronize()
        timings.append((time.perf_counter() - start) * 1000)

    arr = np.array(timings)
    return {
        "p50_ms": float(np.percentile(arr, 50)),
        "p95_ms": float(np.percentile(arr, 95)),
        "max_hz": 1000.0 / float(np.percentile(arr, 95)),
    }


if __name__ == "__main__":
    image = Image.open("test_scene.png")
    print(measure_latency(image, "pick up the red block"))
    for instruction in ["pick up the red block", "pick up the blue block"]:
        action = predict_action(image, instruction)
        print(f"{instruction!r:35} -> {np.round(action, 4)}")
```

> ⚠️ 需核实：`predict_action` 的接口和 `unnorm_key` 的可选值在版本间有变化，以仓库当前 README 为准。

**跑完这一步你应该有两个数：一个动作向量，和一个 p95 延迟。** 用延迟算出你最高能跑多少 Hz，以及需要多大的 chunk_size 才能撑起 30Hz（3.8 节）。

**然后是 LoRA 微调（几小时到一天）。** 用阶段 05 采的数据，但给每条轨迹加语言标注（「pick up the red block」/「pick up the blue block」）。要求：

1. 至少两种物体、两种指令
2. **重算动作归一化统计量**（3.5 节）
3. 评估时分开测「成功率」和「指令跟随准确率」（3.10 节）
4. 和阶段 05 的 ACT 在同样数据量下对比

## 5. 故障实验

**这一节是整个阶段最有价值的部分。** 前四个实验做完，你会对 VLA 的真实能力有一个校准的认识，而且是自己测出来的，不是从论文里读到的。

**实验 1：语言敏感性。**
同一张图，换不同指令：「pick up the red block」/「pick up the blue block」/「move to the left」。
**观察什么：** 动作向量的差异，用余弦相似度量化。如果不同指令给出的动作几乎相同（余弦相似度接近 1），说明模型没在用语言，只是在做视觉反射（3.6 节）。这个数字是判断「语言输入是否真的起作用」的唯一硬证据。

**实验 2：语言鲁棒性。**
同义表述：「pick up the red block」/「grab the red cube」/「take the crimson block」/「拿起红色方块」（中文）。
**观察什么：** 动作的一致性。你会发现它对措辞相当敏感，而中文基本不工作（训练数据几乎全是英文）。记下哪些改写它能容忍、哪些不能——这个边界决定了上游 LLM 规划器应该输出什么格式的指令。

**实验 3：无意义指令。**
输入「do nothing」/「fly to the moon」/「asdfghjkl」/ 空字符串。
**观察什么：** 它会不会输出零动作或者拒绝——**它不会。** VLA 没有「拒绝执行」的概念，任何输入都会得到一个语法上合法的动作向量。这个观察是阶段 08 整个治理层存在的理由，做完请把具体输出记下来。

**实验 4：视觉分布外。**
换一个和训练数据风格差很多的场景：不同背景、不同光照、没见过的物体、相机视角偏移 30 度。
**观察什么：** 动作是否变得毫无意义，以及**它的输出有没有任何变化来提示你它不确定**。没有。置信度不会下降，输出格式不会变，你从输出侧看不出它已经处于分布外。

做完这四个实验，结论应该是：**它是一个有用但脆弱的组件，不是一个可信的决策者。**

**实验 5：unnorm_key 用错。**
故意换一个数据集的统计量做反归一化。
**观察什么：** 动作幅度差几倍。和阶段 05 实验 3 是同一个现象，这里是它在真实项目里的样子。

**实验 6：量化误差实测。**
用 `ActionTokenizer` 对你的数据 encode 再 decode，统计误差分布，和 `quantization_error_bound()` 的理论值对比。
**观察什么：** 误差是否达到你任务的精度要求边界。如果动作范围是 ±0.1 米、256 bin，误差约 0.4 毫米——够不够取决于你抓的是什么。

**实验 7：延迟对闭环的影响。**
用不同 chunk_size（1、5、20、50）部署，测实际控制频率和成功率。
**观察什么：** chunk_size=1 时实际频率降到多少（可能只有 5-10Hz）。成功率随 chunk_size 的曲线是不是单峰的——太小延迟不够，太大开环时间过长。这条曲线就是 3.8 节权衡的实测形态。

**实验 8：微调后忘记重算统计量。**
微调完成后仍用预训练的统计量评估。
**观察什么：** 成功率相比正确设置掉多少。这个数字用来说服未来的自己不要跳过这一步。

**实验 9：语言标注退化。**
把所有训练轨迹的语言标注改成同一个字符串（「do the task」）重新微调。
**观察什么：** 成功率可能几乎不变（说明模型本来就主要靠视觉），但指令跟随准确率会崩。这个对比直接量化了「语言到底贡献了多少」。

## 7. 与 Agent / 后端的类比

**VLA 就是一个不可靠的工具（tool）。** 这是最有用的一个类比。你在 Agent 运行时里对待一个外部 API 的态度——不信任返回值、检查响应格式、设超时、记录调用、准备失败分支——一字不改地适用于 VLA。区别只是它的失败率高一个数量级。

**LoRA 微调完全同构。** 冻结骨干、低秩适配、target_modules 选择、显存权衡，和你做过的 LLM 微调是同一套东西。这部分不需要新知识。

**归一化统计量 = 配置与代码的版本绑定。** 一个跟着 checkpoint 走的元数据文件，加载错就全盘错。你在后端里对待 schema 版本、迁移脚本版本的谨慎，直接搬过来。

**指令跟随准确率 vs 成功率 = 端到端指标要分解。** 一个聚合指标掩盖了两个独立的失败模式。你在 Agent 评测里区分「工具调用成功」和「回答正确」是同一个动作。

**inference latency 预算 = SLA 分解。** 33ms 的预算里图像采集占多少、推理占多少、通信占多少——这就是把端到端延迟目标拆到各个组件的老办法。

**分布外时没有任何信号 = 缺少健康检查。** 一个没有 readiness probe 的服务，你无法知道它是否还能正确工作。VLA 就是这样一个服务，而且没有办法给它加探针（见下一节）。

## 8. 这个类比在哪里失效

「VLA 是一个不可靠的工具」这个类比能带你走很远，但有五处它会骗你。

**1. 它没有错误返回值。** 一个 HTTP 工具失败会给你 4xx/5xx，一个 Python 函数会抛异常。VLA 的失败和成功在输出侧**完全无法区分**——都是一个格式合法的浮点向量。实验 3 和实验 4 就是这个事实的直接演示。这意味着你熟悉的「检查返回码然后分支处理」这个模式在这里根本没有输入。判断成功与否的信息必须从别处（视觉核验）获得，而那需要你自己建，这正是阶段 08。

**2. 它没有置信度，而且加上去的置信度也不可信。** 你可能想说：那就看 logits 的熵。但离散化路线下 action token 的概率分布和「动作是否正确」相关性很弱——模型可以在完全错误的动作上非常自信。这和分类模型的校准问题类似，但更严重，因为动作空间的错误没有「类别」这种离散结构可以校准。

**3. 重试不是幂等的。** 工具调用失败重试一次通常没有副作用。VLA 输出一个动作、执行了、失败了，此时物体位置已经变了。「用同样的输入重试」这件事在物理上不存在——输入（观测）已经不同了。整套幂等和重试的工程直觉在这里失效。

**4. 延迟不是体验问题，是正确性问题。** 后端里延迟高了用户等一会儿。这里延迟高了 chunk 就要变大，开环时间就变长，策略基于过期观测行动的时间窗就变宽——**延迟直接转化成错误率**。你不能通过「加缓存」或者「异步化」绕过它。

**5. 它不是无状态的，但也不是有状态的。** 一个 REST 工具你可以明确说它无状态。VLA 的每次调用形式上无状态（同样输入同样输出），但它嵌在一个有物理状态的世界里，而那个状态它只能通过一张图片间接看到。所以「无状态服务可以随意并发和重放」这个前提不成立——不是因为服务有状态，而是因为世界有状态而服务看不全。
