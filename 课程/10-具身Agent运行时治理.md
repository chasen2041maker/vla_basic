# 阶段 08：具身 Agent 运行时治理

> 把 Agent 运行时的工程能力带进具身。这一阶段的内容是**待验证的研究假设，不是已验证的答案**。不设时间上限 · 硬件可选（MuJoCo 就够）· 产出：一批实验结论，以及可能的一个开源项目

## 1. 为什么要学

### 1.1 这一层确实缺失

具身领域现在的人大多是算法背景，关心的是「策略成功率能不能从 35% 提到 50%」。极少有人在系统层面认真问：

- 一个动作执行前，怎么判断它是否可逆、是否需要人确认？
- 失败之后世界状态已经变了，怎么安全地恢复？
- 长任务执行到一半需要人介入，怎么挂起、怎么续跑、怎么处理超时？
- 整个执行过程怎么留下可审计的证据？
- 多个技能并发时，怎么保证不会互相破坏对方的前置条件？

**这个判断和你是谁无关。** 不管来做这件事的人是有 Agent 运行时背景、有分布式系统背景、还是刚入行，这一层的缺失是这个领域的客观状态：策略层在快速进步，执行治理层几乎空白。所有想把具身系统投入真实场景的人都会撞上它。

这一层的问题在生产级 Agent 运行时里已经解决过：任务生命周期管理（配额预留/提交/退款、ownership 租约、取消、checkpoint 恢复、悬挂状态回收）、人在环挂起（语义 slot 抽取、运行中断点、超时过期），以及 AgentTrust Runtime 的 allow/ask/deny 加持久化审批加哈希链证据。**搬到机器人上，就是具身领域缺的那一层。**

所以这一阶段的定位是：不是学新东西，是把已有的能力翻译到新领域。

### 1.2 但「翻译过来能用」是假设，不是结论

上面那段话里有一个没被验证的跳跃：**「文本 Agent 里有效的机制，翻译到物理世界之后仍然有效」。**

这个跳跃可能在多个地方断裂：

- 后置视觉核验的检出率也许太低，或者误报率高到让机器人频繁误停
- 可逆性分级也许在实际任务里没有区分度（大部分动作都落在同一档）
- 补偿动作也许在物理世界里成功率太低，补偿本身成为新的失败源
- HITL 挂起恢复也许在真实场景里几乎总是「无法恢复」，从而变成一个昂贵的摆设

**这些都是可以做实验回答的问题，而这一阶段的正确做法是先做实验。**

所以本文第 3 节的组织方式是「假设 + 实验 + 指标」，而不是「设计 + 实现」。第 4 节给出的代码是**一种候选实现，待验证**——它的价值在于让实验能跑起来，不在于它是正确答案。

**两件事要分清：**

| | 状态 |
|---|---|
| 「这一层缺失，值得做」 | 这是判断，我认为它成立，理由见 1.1 |
| 「用 Saga / 可逆性分级 / 证据链这套具体方案做」 | 这是假设，需要实验验证 |

前者不因为后者没验证而动摇。如果第 3 节的四个假设全部被推翻，结论是「这套方案不对」，不是「这一层不缺失」。

### 1.3 一个已经确立的事实

有一件事不需要假设，前面两个阶段已经验证过：

**策略本身没有失败识别能力。**

- 阶段 06 实验 3：VLA 对任何输入（包括「fly to the moon」和乱码）都输出一个格式合法的动作，不会拒绝
- 阶段 06 实验 4：视觉分布外时输出照样「自信」，从输出侧看不出它已经失效
- 阶段 05：ACT 策略抓空了也会继续执行后面的放置动作，因为它只是在做序列预测

**所以「动作执行后核验结果状态」这件事，策略层不可能自己提供。** 它必须来自外面的一层。这是整个阶段最硬的一块地基，也是假设 1 的出发点。

## 2. 学完后必须能回答

- 在你的任务里，「策略报告成功但实际失败」的比例是多少？这个数字是怎么测的？
- 后置视觉核验的检出率和误报率各是多少？误报造成的额外停机值不值这个检出率？
- 你的可逆性分级在实际任务里有区分度吗？各档的动作占比是多少？
- 补偿动作的成功率是多少？补偿失败的情况占多少？
- HITL 挂起后，`can_resume` 判断正确的比例是多少？误判为「可恢复」的后果是什么？
- 核验和门禁给控制循环增加了多少毫秒？这个开销把控制频率压到了多少？
- 上面每一个数字，你是自己测的还是推测的？

## 3. 核心概念

### 3.1 能力映射表

先把已有的东西和具身的需求对应起来。这张表是整个阶段的路线图。

| 文本 Agent 运行时里的机制 | 具身里对应的问题 | 难度变化 |
|---|---|---|
| ToolIntent/ToolResult 统一管线 | 技能调用的统一契约 | 相同 |
| allow / ask / deny 权限门禁 | 动作执行前的可逆性与授权判断 | 更重要（后果物理化） |
| 持久化审批 | 人在环确认，跨进程重启存活 | 相同 |
| 哈希链证据 | 执行过程的防篡改审计 | 相同 |
| HITL 挂起问人、超时过期 | 「杯子里有水，要继续吗」 | 相同，但触发条件来自感知 |
| 任务生命周期 + checkpoint 恢复 | 长任务中断后从哪续 | 更难（世界状态无法回滚） |
| 配额预留/提交/退款 | 资源与时间预算管理 | 相同 |
| Outbox + 幂等 | 目标态 reconcile | 语义变化，见假设 3 |
| reaper / recovery worker | 悬挂任务、超时、僵死状态回收 | 相同 |
| GroundGuard report_only 事实门禁 | 动作前的前置条件校验、动作后的结果核验 | 强类比，见假设 1 |
| 失败类型细分 | 决定重试/重规划/求助 | 更重要 |

看这张表你会发现大部分是「相同」。这不是巧合——**Agent 运行时解决的一直是「不可靠工具 + 有状态长任务 + 需要审批和审计」这一类问题**，具身只是把工具从 shell 命令换成了机械臂。

真正变化的只有两处：世界状态不可回滚（假设 3），以及前置条件来自带噪声的感知（假设 1）。

**但「相同」这一列本身也是待验证的。** 这张表是分析产物，不是实验结论。下面四个假设就是用来检验它的。

### 3.2 四个假设

每个假设的结构一致：**假设内容 → 实验设计 → 指标 → 可能被推翻的方式**。最后一项很重要——一个说不出「什么结果会推翻我」的假设不是假设，是信念。

---

### 假设 1：动作后置核验可以发现策略静默失败

**假设内容：** 在技能执行后加一层独立的视觉核验（比较「期望状态」和「观测状态」），能检出相当比例的静默失败——即策略报告成功但物理状态不符的情况。这一层的检出能力来自它使用了策略没有使用的信息通道（执行后的新观测），而不是来自更好的模型。

**为什么值得测：** 1.3 节已经确立策略没有失败识别能力。但「策略做不到」不等于「加一层就能做到」——核验本身也是一个感知问题，也会错。

**实验：** 故意让夹爪没抓住物体但技能返回成功，观察运行时能否通过视觉发现。

具体做法（仿真里就能做，MuJoCo 足够）：

1. 在阶段 05 或 07 的策略外面包一层后置核验
2. 构造三类静默失败场景：
   - 抓空（夹爪闭合但物体不在夹爪之间）
   - 抓到后滑落（中途掉落，但技能已返回成功）
   - 抓错物体（抓了蓝块而指令是红块）
3. 每类跑 50 次，记录核验层的判断
4. 同时跑 50 次正常成功的情况，测误报

**指标：**

| 指标 | 定义 | 及格线（我的猜测，待验证） |
|---|---|---|
| **检出率** | 真实静默失败中被核验层发现的比例 | > 70%？ |
| **误报率** | 实际成功但被判为失败的比例 | < 5%？ |
| **额外延迟** | 核验带来的每步耗时增加（毫秒） | 不超过控制周期的 20%？ |
| **对最终成功率的影响** | 接入核验和重试后，端到端任务成功率的变化 | 应该为正，但可能为负 |

最后一个指标是关键。**检出率高不代表系统更好用**——如果误报导致大量不必要的重试或停机，端到端成功率可能下降。这个数字才是这一层是否值得存在的判据。

**及格线上的问号是刻意的。** 我不知道合理阈值是多少，这正是要测的东西。填上你自己的数字，那才是知识。

**可能被推翻的方式：**

- 检出率低于 40%：说明视觉核验对这类失败不敏感，需要换传感器（力/触觉）而不是换算法
- 误报率高于 20%：说明判据阈值找不到好的工作点，这一层带来的麻烦大于收益
- 额外延迟超过控制周期：说明必须异步核验，那会引入「发现失败时已经又执行了几步」的新问题
- 端到端成功率下降：最严重的推翻方式，说明整个思路有问题

**必做的前置测量：** 先不加任何核验，纯统计「策略自己报告成功、但人工检查发现失败」的比例。这个基线数字通常会让你意外，而且它是后面所有讨论的前提——如果静默失败只占 2%，这一层的价值就有限。

### 假设 2：可逆性分级可以降低不可恢复错误的发生率

**假设内容：** 按「出错后能否恢复以及恢复成本」给动作分级，并对高不可逆性的动作强制人工确认，能显著降低不可恢复错误的发生率，且付出的人工确认成本可以接受。

**为什么值得测：** 分级听起来合理，但有两个可能致命的问题。一是**区分度**：如果实际任务里 95% 的动作都落在「完全可逆」这一档，分级就是无用的复杂度。二是**分级本身要靠预测**：执行前你不知道这个动作会不会打碎东西，你只能基于动作类型和置信度猜。

**实验：**

1. 取阶段 04 或 07 的一个多步任务，枚举所有会执行的动作，逐个打上可逆性标签
2. 统计各档的动作占比——**这一步就能验证区分度**，如果分布极度集中，假设 2 直接失败
3. 构造一批会导致不可恢复后果的场景（把物体推下桌子、把液体倒出、把易碎物压坏）
4. 分两组各跑 50 次：A 组无门禁全自动执行，B 组按分级对 IRREVERSIBLE 及以上要求确认
5. 对比两组的不可恢复错误次数和总耗时

**指标：**

| 指标 | 定义 |
|---|---|
| **分级区分度** | 各档动作的占比分布（熵，或者最大档占比） |
| **不可恢复错误率** | 每 100 次任务里发生不可恢复后果的次数，A 组 vs B 组 |
| **人工确认次数** | B 组平均每个任务打断人多少次 |
| **误拦率** | 被要求确认但人确认后照常执行的比例（说明这次拦截没必要） |
| **任务耗时增加** | B 组相对 A 组的时间开销 |

**误拦率是最有意思的一个。** 如果 90% 的确认请求人都直接点「继续」，这个门禁在做的事情就是消耗人的注意力，而且人会很快养成不看内容就点确认的习惯——那时它比没有更糟，因为它给了虚假的安全感。

**可能被推翻的方式：**

- 最大档占比超过 85%：分级没有区分度
- 误拦率超过 70%：门禁的判据太粗，人的确认变成橡皮章
- 不可恢复错误率两组没有统计显著差异：门禁没起作用（可能因为错误发生在被判为「可逆」的动作上）
- 人工确认次数高到任务无法自动化：这一层把自主系统变成了遥操作

**必做的设计练习（纯思考，但决定后面所有设计的质量）：** 为下面这些动作定级，并写出补偿动作或论证它无法补偿：

1. 移动到某个位置
2. 抓起一个物体
3. 把物体从 A 放到 B
4. 打开抽屉
5. 把水从杯子倒进碗里
6. 把两块积木叠起来
7. 按下电源按钮

第 5 和第 7 是不可补偿的（point of no return）。第 4 和第 6 是「可补偿但不完美」。做完这个练习你会对可逆性分级有实感，也会发现给一个动作定级比想象的难——同一个「抓起物体」，抓的是方块还是鸡蛋，答案不同。

### 假设 3：补偿（compensation）能在物理世界替代回滚（rollback）

**假设内容：** 为每个动作定义一个补偿动作，失败时反向执行补偿序列，可以把系统带回一个「可接受状态」——虽然不是原状态。这个模式（Saga）在足够多的物理任务上可行，且可行边界能被清晰界定。

**为什么值得测：** 这是从后端搬过来时**唯一需要根本重新设计**的地方，所以也是最可能失败的地方。后端 Saga 的隐含前提是「补偿动作一定能成功」——转账失败就退款，退款不会失败。物理世界没有这个保证：把杯子移回原位的动作本身也可能失败，而且可能失败得更糟。

**核心语义差异必须先说清：**

- **回滚**保证「状态回到操作前」
- **补偿**只保证「达到一个可接受的状态」

「把杯子从桌上移到架子上」的补偿是「把杯子移回桌上」，但杯子的朝向可能变了、位置差几厘米。这是可接受的，不是完美还原。这个语义差异必须在设计时就承认，否则你会写出假设补偿完美的上层逻辑。

**实验：**

1. 取三类任务：单步可逆（移动）、多步可逆（A 到 B 搬运）、含不可逆步骤（倒水或叠塔）
2. 为每一步写补偿动作，标记哪些无补偿（point of no return）
3. 在每一步注入失败，触发补偿序列
4. 记录补偿后的实际状态与初始状态的偏差
5. 特别测：**补偿动作自己失败时会怎样**

**指标：**

| 指标 | 定义 |
|---|---|
| **补偿成功率** | 补偿动作本身成功执行的比例 |
| **状态偏差** | 补偿后状态与初始状态的距离（位置差、朝向差） |
| **二次破坏率** | 补偿过程反而让场景更糟的比例 |
| **不可补偿点占比** | 任务中无法定义补偿的步骤比例 |
| **越过不可返回点后的可恢复性** | 越过之后失败，人工介入的必要比例 |

**二次破坏率是这个假设的生死线。** 如果补偿有 20% 的概率让场景变得更糟（比如移回杯子时把旁边的东西撞倒），那么「不补偿、直接停下等人」可能是更好的策略。这个数字会直接决定 Saga 在物理世界值不值得做。

**三个必须在实现里体现的差异：**

1. **补偿本身可能失败**，且不能无限重试——可能越补越糟。失败后必须升级到人工介入。
2. **补偿前必须重新观测。** 世界可能已经变了，按记忆执行补偿可能造成新的破坏。
3. **越过 point of no return 后，前面的补偿可能变得无意义。** 已经把水倒进杯子，再把杯子移回原位没有意义了。

**可能被推翻的方式：**

- 二次破坏率超过 15%：补偿的期望收益为负
- 补偿成功率低于 60%：补偿机制不可靠到无法依赖
- 不可补偿点占比超过 50%：大部分任务根本走不到补偿这一步，机制没有用武之地
- 状态偏差大到后续动作无法基于补偿后状态继续：补偿只是形式上完成了

### 假设 4：HITL 挂起与恢复在物理世界能保持正确性

**假设内容：** 长任务执行中挂起问人、等待回答、然后从挂起点恢复，这套机制在物理世界可以正确工作——前提是加上两个具身特有的处理：挂起前进入安全停放状态，恢复前校验世界是否仍然可恢复。

**为什么值得测：** 文本 Agent 的挂起恢复很干净——上下文冻结，回答到了继续跑。物理世界有两个新问题：机器人挂起期间必须物理上安全（不能举着重物等一小时），以及人回答完之后世界可能已经不是挂起时的样子了。

**触发源的差异也值得注意：** 文本场景的 elicitation 触发源是「指令里缺字段」，具身场景多了一个「感知发现意外状态」——机器人走到跟前发现杯子里有水。后者是新的，也是有意思的部分。

**实验：**

1. 在阶段 06 的 agent 里加一个挂起触发点（比如场景里放一个标记为「装了液体」的杯子，agent 要抓它时挂起问人）
2. 测试三种情况：
   - 人及时回答，正常恢复
   - 人不回答，超时后系统如何处理
   - **人回答之前，你手动把杯子拿走** —— 观察 `can_resume` 是否正确拒绝恢复
3. 挂起期间检查机器人状态：是否举着物体？关节是否持续受力？
4. 每种情况跑 20 次

**指标：**

| 指标 | 定义 |
|---|---|
| **can_resume 判断准确率** | 世界已变时正确拒绝恢复的比例 |
| **假阳性（误判可恢复）** | 世界已变但判定可恢复，继续执行导致错误的次数 |
| **安全停放成功率** | 挂起时成功进入安全状态的比例 |
| **停放期间的硬件状态** | 关节力矩、（真机上）舵机温度 |
| **恢复后任务完成率** | 恢复的任务里最终成功完成的比例 |

**假阳性是这里最危险的指标。** 误判为「可恢复」意味着机器人拿着过期的世界认知继续动作——比故障 2（stale observation）更糟，因为中间隔了很长时间，世界变化更大。

第三种测试情况（挂起期间手动改变世界）是文本 Agent 里完全不存在的，务必做。

**可能被推翻的方式：**

- 假阳性率超过 10%：恢复机制不安全，宁可全部拒绝恢复、重新开始
- 安全停放失败（挂起时无法放下物体）：说明挂起在某些状态下不可行，需要限制挂起时机
- 恢复后任务完成率很低：说明恢复的价值不大，不如直接重新规划整个任务

### 3.3 一种候选实现

下面的代码是**候选实现，不是答案**。它按上面四个假设的设计意图写成，但每一个设计选择都还没有被验证。

先跑假设的实验，拿到数字，再决定这些代码该怎么改——或者该不该存在。

```python
"""物理动作的可逆性分级。

分级依据不是「危险程度」，而是「出错后能否恢复以及恢复成本」。
这个区分很重要：一个动作可能很安全但不可逆（把糖倒进咖啡），
也可能看着吓人但完全可逆（快速移动到某个位置）。

⚠️ 这套分级的区分度是假设 2 要验证的东西。如果实际任务里
动作分布极度集中在某一档，说明这个维度选错了。
"""

from dataclasses import dataclass, field
from enum import Enum, IntEnum


class Reversibility(IntEnum):
    """可逆性等级，数值越大越不可逆。

    分级依据是「撤销这个动作需要什么」：

    FULLY_REVERSIBLE: 反向执行同一动作即可撤销。
      例：移动到某个位置、张开夹爪

    REVERSIBLE_WITH_EFFORT: 可以撤销，但需要额外动作序列且可能失败。
      例：把物体从 A 移到 B

    PARTIALLY_IRREVERSIBLE: 主要状态可恢复，但有副作用残留。
      例：把积木塔推倒（可以重建，但顺序可能不同）

    IRREVERSIBLE: 无法通过机器人自身动作撤销。
      例：倒出液体、按下不可复位的按钮

    DESTRUCTIVE: 不可逆且造成损害。
      例：打碎物体、撞坏设备、伤到人
    """

    FULLY_REVERSIBLE = 0
    REVERSIBLE_WITH_EFFORT = 1
    PARTIALLY_IRREVERSIBLE = 2
    IRREVERSIBLE = 3
    DESTRUCTIVE = 4


class AuthorizationMode(str, Enum):
    """授权模式，对应 AgentTrust 的 allow/ask/deny。"""

    ALLOW = "allow"
    ASK = "ask"              # 需要人确认，阻塞等待
    ASK_ASYNC = "ask_async"  # 挂起任务而非阻塞，见假设 4
    DENY = "deny"


@dataclass
class ActionRisk:
    """一个动作的风险评估。

    reversibility 和 confidence 是两个独立维度：一个「可逆」但
    「低置信度」的动作也可能需要确认——低置信度意味着你不确定
    它到底会做什么。
    """

    reversibility: Reversibility
    confidence: float
    affects_objects: list[str] = field(default_factory=list)
    notes: str = ""

    def required_authorization(
        self,
        *,
        confidence_threshold: float = 0.7,
    ) -> AuthorizationMode:
        """根据风险决定授权模式。

        ⚠️ 这里的阈值和升级规则全是猜的。假设 2 的「误拦率」
        指标就是用来校准它们的。如果误拦率极高，说明这套
        规则太保守。
        """
        if self.reversibility >= Reversibility.DESTRUCTIVE:
            # 一律拒绝，不给人确认的机会——人也可能误点，
            # 而这一档的后果不可承受
            return AuthorizationMode.DENY

        if self.reversibility >= Reversibility.IRREVERSIBLE:
            return AuthorizationMode.ASK_ASYNC

        if self.confidence < confidence_threshold:
            if self.reversibility >= Reversibility.PARTIALLY_IRREVERSIBLE:
                return AuthorizationMode.ASK_ASYNC
            return AuthorizationMode.ASK

        return AuthorizationMode.ALLOW
```

门禁模式沿用 GroundGuard 的 report_only 优先原则：

```python
class GateMode(str, Enum):
    """门禁模式。

    先 report_only 观测、积累数据、确认判据可靠，再开 enforce。
    这个上线姿势在物理系统上比在文本系统上更重要，因为误阻断
    会让机器人在半途卡死。

    SAFE_STOP 是物理系统特有的第三种模式：检测到问题时不是
    拒绝执行，而是让机器人进入安全状态后停下等人。
    """

    REPORT_ONLY = "report_only"
    ENFORCE = "enforce"
    SAFE_STOP = "safe_stop"
```

证据链（用于假设 1 到 4 的所有实验数据采集）：

```python
"""执行证据链。

即使在 REPORT_ONLY 模式下也要完整记录——它是你后续决定
判据阈值的唯一数据来源。

注意 commanded_action 和 executed_action 分开记录：安全层
可能修改了动作，事后排查必须能区分「策略想做什么」和
「实际做了什么」。
"""

import hashlib
import json
import time
from dataclasses import asdict, dataclass, field


@dataclass
class ExecutionRecord:
    """一条执行记录。"""

    sequence: int
    timestamp: float
    action_name: str
    commanded_action: list[float]
    executed_action: list[float]
    safety_triggers: list[str]
    observation_hash: str
    authorization: str
    risk_level: int
    verification: dict | None
    prev_hash: str

    def compute_hash(self) -> str:
        """计算这条记录的哈希。

        用 sort_keys 保证序列化确定性——否则字典顺序变化
        会导致同一条记录算出不同哈希。
        """
        payload = json.dumps(asdict(self), sort_keys=True, ensure_ascii=False)
        return hashlib.sha256(payload.encode("utf-8")).hexdigest()


@dataclass
class EvidenceChain:
    """append-only 证据链，可检出任何历史篡改。"""

    records: list[ExecutionRecord] = field(default_factory=list)
    _last_hash: str = "0" * 64

    def append(self, **kwargs) -> ExecutionRecord:
        record = ExecutionRecord(
            sequence=len(self.records),
            timestamp=time.time(),
            prev_hash=self._last_hash,
            **kwargs,
        )
        self._last_hash = record.compute_hash()
        self.records.append(record)
        return record

    def verify(self) -> tuple[bool, str]:
        expected_prev = "0" * 64
        for record in self.records:
            if record.prev_hash != expected_prev:
                return False, f"记录 {record.sequence} 的 prev_hash 失配"
            expected_prev = record.compute_hash()
        return True, f"链完整，共 {len(self.records)} 条记录"
```

```python
@dataclass
class SilentFailureBaseline:
    """静默失败基线。

    这是整个阶段的第一个数字，也是最重要的一个。
    如果静默失败只占 2%，后面所有假设的价值都要打折。
    """

    total_runs: int
    reported_success: int
    actually_success: int

    @property
    def silent_failure_rate(self) -> float:
        """策略报成功但实际失败的比例。"""
        false_success = self.reported_success - self.actually_success
        return false_success / self.total_runs if self.total_runs else 0.0
```

## 5. 故障实验

这个阶段的故障实验有个特点：**它们测的是治理层本身的失效模式**，而不是机器人的失效模式。

### 故障 1：核验层误报

故意把后置核验的容差调得极紧（比如位置容差 2mm）。

**观察什么**：大量成功的动作被判为失败，触发不必要的重试。统计端到端成功率——它会下降。这演示了「检出率高不等于系统更好」。

### 故障 2：门禁变成橡皮章

把授权阈值调得极保守（所有 `REVERSIBLE_WITH_EFFORT` 及以上都要求确认），然后自己扮演人连点 20 次确认。

**观察什么**：你会发现自己在第 5 次之后就不看内容了。这就是误拦率过高的真实后果——门禁给了虚假的安全感，比没有更糟。

### 故障 3：补偿造成二次破坏

在场景里放多个物体，让补偿路径经过其他物体。触发一次需要补偿的失败。

**观察什么**：补偿动作撞倒了旁边的东西。记录这个概率——如果超过 15%，「直接停下等人」比补偿更好。

### 故障 4：补偿前不重新观测

去掉补偿序列里的重新观测步骤，按挂起时的记忆执行补偿。

**观察什么**：补偿动作作用在错误的位置上，可能把场景弄得更乱。

### 故障 5：跳过 report_only 直接 enforce

把门禁直接设成 `ENFORCE`，用未经校准的判据。

**观察什么**：机器人在任务半途被误阻断卡死。这演示了为什么 report_only 优先不是保守，是必要——**误阻断在物理系统上的后果是机器人停在一个尴尬的姿态，可能还举着东西。**

### 故障 6：证据链篡改检测

手动修改证据链中间一条记录的 `commanded_action`，然后跑 `verify()`。

**观察什么**：应该在被改的那条记录之后报 `prev_hash` 失配。如果没检出，你的哈希实现有问题（常见原因是 `sort_keys` 漏了）。

### 故障 7：核验层增加的延迟压垮控制频率

把核验放进控制循环的同步路径里，测每步耗时。

**观察什么**：如果核验需要一次完整的视觉推理（几十毫秒），控制频率会从 30Hz 掉到 10Hz 以下。这引出一个真实的设计问题：**核验必须异步**，而异步意味着「发现失败时已经又执行了几步」——这是假设 1 里列出的推翻条件之一。

## 7. 与 Agent / 后端的类比

这一整章都建立在类比之上，所以这一节和下一节尤其重要。

**可逆性分级 ↔ 工具风险分级。** AgentTrust 里按「文件读 / 文件写 / shell / git / MCP」分类工具风险，本质也是可逆性——`ls` 和 `rm -rf` 的区别就是能不能撤销。物理世界让这个维度从隐含变成了一等公民。

**allow/ask/deny 门禁 ↔ 权限校验。** 结构完全一致：执行前判断、按风险分档、高风险需人工确认。

**Saga 补偿 ↔ 分布式事务。** 跨服务事务用 Saga 而不是 2PC，因为无法对外部服务加锁。物理世界用 Saga 而不是回滚，因为无法对现实加锁。

**证据链 ↔ 审计日志 + 哈希链。** 完全相同的实现，只是记录的内容从 API 调用变成了动作和观测。

**report_only 优先 ↔ 灰度发布。** 先观测不阻断，积累数据确认判据可靠，再开强制。GroundGuard 用的就是这个姿势。

**后置核验 ↔ 写后读校验。** 「写完再读一遍确认真的写进去了」的物理版本。

**HITL 挂起 ↔ 异步审批工作流。** 任务挂起、等外部输入、超时过期、恢复续跑——这套机制在文本 Agent 里已经成熟。

## 8. 这个类比在哪里失效

这一节是整章最需要认真读的部分。**上面每个类比都很顺，而「顺」恰恰是危险信号**——它会让你以为问题已经解决了，只是换了个场景。

**「Saga 补偿就是分布式事务」失效在补偿的可靠性上。** 后端 Saga 的隐含前提是补偿动作一定成功——转账失败就退款，退款不会失败。物理补偿会失败，而且可能失败得更糟（故障实验 3 的二次破坏）。后端 Saga 里没有「补偿把系统弄得更乱」这个分支，物理 Saga 必须有。

**「门禁就是权限校验」失效在判断时机上。** 后端的权限判断是确定的：这个 token 有没有这个 scope，答案唯一。物理动作的风险评估是**预测**——执行前你不知道这次抓取会不会打碎杯子，只能基于动作类型和置信度猜。你在给一个概率分布打标签，而不是查一张权限表。

**「报告成功但实际失败」这个类比看起来一样，但可检测性完全不同。** 后端的「接口返回 200 但数据没写进去」可以通过读数据库确认，读出来的是真值。物理核验用的是另一个带噪声的观测——**核验层自己也会错**（这就是误报率存在的原因）。你不是在用真值检查执行结果，是在用一个不可靠的观测检查另一个不可靠的执行。

**「审计日志」失效在原始数据的体积上。** 后端可以记录完整的请求体和响应体。物理系统一次任务几百帧图像，全存会爆炸，所以只能存哈希——**这意味着事后你无法重新审视当时到底看到了什么**，除非另外做图像归档。审计的完整性被物理数据量削弱了。

**「HITL 挂起就是异步审批」失效在挂起期间的状态维护上。** 文本任务挂起时，上下文冻结在内存或数据库里，一小时后完全一致。机器人挂起时：世界在继续演化（物体会滑落）、机器人自己在消耗能量（举着东西的关节会发热）、人可以随时拿走目标物体。**「冻结状态」这个概念在物理世界不存在。**

**「report_only 就是灰度」失效在误动作的代价上。** 灰度发布里，新逻辑判断错了最多影响一小部分请求，可以回滚。物理系统的误阻断会让机器人停在一个尴尬姿态（可能还举着东西），误放行会造成不可逆后果。两个方向的错误都比灰度发布贵得多。

**一个最根本的问题：这一整套类比的存在本身就是风险。**

你熟悉这些模式，所以看到具身问题时会自动映射过去。映射对的时候很省力，映射错的时候你甚至不会意识到自己在用错误的框架思考——因为一切都「说得通」。

这也是为什么这一章的结构是假设而不是答案。**四个假设本质上是在检验「这个类比到底成立到什么程度」**，而不是在实现一个已知正确的方案。3.1 那张能力映射表里的「相同」，每一个都是待验证的猜测。

## 结语

这个阶段的定位判断是成立的：具身领域客观上缺这一层。策略本身没有失败识别能力（阶段 08 的实验会实证这点），而做策略的人不解决这个问题，做控制的人也不解决。这个空缺独立于你是谁。

但「这个方向有空缺」和「我的方案是对的」是两件事。

所以这一章没有给你一个可以直接实现的方案，给的是四个假设、四组实验、和每个假设被推翻的条件。跑完实验，你手里会有别人没有的数字——那才是差异化，而不是一份设计文档。

同时，阶段 01 到 09 必须认真补完。在 VLA 和控制上你很难比 CV 博士和十年控制经验的人强，这是现实；但没有那些基础，这一章只会变成用熟悉的词汇重新包装不熟悉的问题。
