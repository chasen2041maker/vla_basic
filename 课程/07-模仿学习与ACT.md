# 阶段 05：模仿学习与 ACT

> 从数据出发理解模仿学习：先说清一条 episode 里每个字段到底是什么，再谈模型结构。预估投入 15-25 小时 · 需要 GPU（本地卡或云上按小时租都行，无需硬件机器人）

## 1. 为什么要学

前四个阶段的技能层都是手写代码：IK 求解加轨迹插值。这个方法对刚性方块抓取够用，但对以下情况会失效：

- 柔性物体（毛巾、线缆）——没有明确的「位姿」可求
- 需要接触反馈的任务（插拔、开抽屉）——纯位置控制会硬顶
- 难以用规则描述的动作（叠衣服、倒水）

模仿学习换一条路：采集人类演示数据，让模型学出「看到什么就做什么」的映射。

在整个具身系统里，这一层是「小脑」——负责把一句原子指令变成连续的关节指令。上面是阶段 04 的 LLM 规划层，下面是阶段 07 的真机执行与安全过滤。阶段 06 的 VLA 是这一层的升级版，但它的数据格式、动作表示、评估方法全部继承自这里。**这一阶段没搞清楚的东西，到 VLA 阶段会以更难排查的形式再出现一次。**

**这一阶段的组织顺序和多数教程相反：先讲数据，再讲模型。**

原因是一个反复出现的现象：很多人能背出 ACT 的 Transformer 有几层编码器、CVAE 的 KL 权重怎么调，但你问他「你数据集里第 37 帧那个 action，7 个数字分别是什么单位、是绝对值还是增量」，他答不上来。而后者才是策略不工作时的真实原因。模型结构是现成的，数据契约是你自己定的，只有你能搞错。

**顺带说清为什么是模仿学习而不是强化学习。** 两条路都能得到策略，选择逻辑：

| | 模仿学习（IL） | 强化学习（RL） |
|---|---|---|
| 需要什么 | 人类演示数据 | reward 函数 + 大量试错 |
| 真机可行性 | 高，几十条演示就能起步 | 低，需要几十万次交互 |
| 主要难点 | 数据质量、分布偏移 | reward 设计、sim2real |
| 失败模式 | 遇到没见过的状态就乱 | 学会作弊、钻空子 |
| 上手成本 | 低 | 高 |

真机操作任务几乎都用 IL，原因很简单：RL 要在真机上试错几十万次，机器人会先坏掉。RL 主要用在仿真里能大规模并行的场景（腿足 locomotion 是典型）。

reward 设计有多难值得你亲自体会一次。用 `stable-baselines3` 训一个「把方块推到目标点」的策略，你会看到它学出各种荒谬的作弊行为：把方块弹飞到目标点上方、卡在边缘反复抖动骗 reward、或者干脆学会不动（因为动了扣分更多）。

💡 联系你的经验：这和你给 LLM 写评测指标时遇到的问题一样——指标写得不严密，模型就会优化指标而不是优化你真正想要的东西。物理世界里这个现象更直观。

## 3. 核心概念

### 3.1 一条 episode 是什么

数据集的最小单位不是「一帧」，是**一条 episode**：从环境 reset 到任务结束（成功、失败或超时）的完整一次尝试。

一条 episode 就是两个等长的序列，加上一点元信息：

```
observations: [obs_0, obs_1, ..., obs_{T-1}]
actions:      [act_0, act_1, ..., act_{T-1}]
success:      True / False
metadata:     任务描述、初始状态、控制频率、采集时间...
```

**对齐约定是整条流水线里最容易错、也最难查的地方。** 约定必须写下来并全程一致：

```
obs_t 是执行 act_t 之前的观测
```

也就是说 `obs_t` 和 `act_t` 同一个下标，表示「在这个状态下，专家做了这个动作」。错位一帧的后果是模型学出滞后一步的行为——策略看起来「几乎对」，但总是慢半拍，抓取时永远差一点。这类 bug 不会报错，只会让成功率无声地掉一档。

```python
"""一条演示轨迹的数据结构与采集。

关键设计点都写在注释里，每一条都是踩过的坑。
"""

from dataclasses import dataclass, field

import numpy as np


@dataclass
class Episode:
    """一条演示轨迹。

    对齐关系：observations[t] 是执行 actions[t] 之前的观测。
    这个约定必须全程一致（采集、训练、部署三处），
    错位一帧会让模型学出滞后的行为，而且不会报任何错。

    metadata 里必须记录 control_hz 和动作表示类型。
    半年后你回来看这份数据，靠记忆是靠不住的。
    """

    observations: list[dict[str, np.ndarray]] = field(default_factory=list)
    actions: list[np.ndarray] = field(default_factory=list)
    success: bool = False
    metadata: dict = field(default_factory=dict)

    def __len__(self) -> int:
        return len(self.actions)


def collect_episode(
    env,
    expert,
    max_steps: int = 400,
    randomize: bool = True,
) -> Episode:
    """采集一条演示轨迹。

    重要：即使失败的轨迹也要记录并保留 success 标记。
    很多人只保存成功轨迹，但失败数据在两个地方有用：
      1. 分析失败模式，改进专家或场景设计
      2. 某些算法（如带 reward 的 IL）可以利用负样本
    过滤在训练时做，不要在采集时做——采集是不可逆的。
    """
    episode = Episode()
    obs = env.reset(randomize=randomize)

    for step in range(max_steps):
        action = expert.act(obs)
        if action is None:
            # 专家自己放弃了（比如 IK 无解）
            episode.metadata["abort_reason"] = "expert_gave_up"
            break

        # 先记录观测，再记录动作，保证对齐
        episode.observations.append(obs)
        episode.actions.append(action)

        obs, done, info = env.step(action)
        if done:
            episode.success = info.get("success", False)
            break

    episode.metadata["steps"] = len(episode)
    return episode
```

**在仿真里采数据的两种方式：**

方式一，脚本专家。你在阶段 02-03 写的 IK 加插值流程就是一个「专家」，让它跑 100 次，每次随机化物体初始位置。最省事，缺点是数据太完美——全是成功轨迹，动作风格单一，模型学不到纠错能力。

方式二，键盘或手柄遥操作。你自己操作机械臂完成任务。数据更像人类，但采集慢且累。

### 3.2 observation 是什么

一个 observation 是模型在决策时刻能看到的全部信息。它是一个字典，典型内容：

| 字段 | 形状 | 说明 |
|---|---|---|
| `images["top"]` | (H, W, 3) uint8 | 顶部相机图像 |
| `images["wrist"]` | (H, W, 3) uint8 | 腕部相机图像 |
| `joint_positions` | (n,) float32 | 当前关节角度，弧度 |
| `gripper_state` | (1,) float32 | 夹爪当前开合度 |

**关于 observation 只有三条硬规则，但每条都能毁掉整个数据集：**

**1. 不要放物体真值位置。** 仿真里 `data.xpos` 唾手可得，放进去模型会立刻学会依赖它——真机上没有这个字段，策略直接失效。这是仿真训练最常犯的错。检查方法：把观测里的真值字段全部置零重新评估，成功率如果崩了就说明模型确实在依赖它。

**2. 观测里必须包含机器人自身状态。** 只给图像不给关节角，模型得从图像里反推自己在哪，这件事很难而且不必要。

**3. 训练和部署的观测必须逐字节一致。** 图像尺寸、通道顺序（RGB vs BGR）、归一化参数、裁剪方式。这里差一点策略就完全不工作，而现象是「机器人乱动」，不会给你任何错误提示。

💡 联系你的经验：第 3 条本质是特征工程的训练/服务一致性问题。区别是这里的失败表现不是准确率下降几个点，而是行为彻底错乱。

### 3.3 action 是什么：六种表示，必须分清

这一节是整个阶段的核心。**如果这一节你看完能准确说出自己数据里 action 的语义，后面所有的坑会少一半。**

同样一个 7 维向量，可能是六种完全不同的东西：

| 表示 | 含义 | 维度示例 | 单位 | 优点 | 缺点 |
|---|---|---|---|---|---|
| **绝对关节角** | 每个关节的目标角度 | 6 关节 + 1 夹爪 | 弧度 | 无累积漂移、可直接下发给位置舵机 | 对本体绑死、初始位置变化不泛化 |
| **关节角增量** | 相对当前角度的变化量 | 同上 | 弧度 | 对初始位置泛化好、数值范围小易归一化 | 误差会累积、必须知道「当前」是什么 |
| **绝对末端位姿** | 末端在基座坐标系的位姿 | xyz + 旋转 + 夹爪 | 米 / 弧度或四元数 | 跨本体、语义直观 | 需要 IK、可能无解或跳解 |
| **末端位姿增量** | 相对当前位姿的变化 | Δxyz + Δ旋转 + 夹爪 | 米 / 弧度 | 跨本体最常用、VLA 的标配 | 误差累积、旋转增量的表示有多种约定 |
| **关节速度** | 每个关节的目标角速度 | 6 + 1 | 弧度/秒 | 平滑、适合速度接口硬件 | 需要积分、静止状态是 0 向量（数据里大量零） |
| **夹爪状态** | 单独一维，开合 | 1 | 归一化 0-1 或米 | —— | 二值还是连续、0 是开还是关，各家不一致 |

关键区别，逐条说清：

**绝对 vs 增量。** 绝对表示里 `action[0] = 0.35` 意思是「1 号关节转到 0.35 弧度」；增量表示里同一个数字意思是「1 号关节再转 0.35 弧度」。两者的数值范围差一个量级以上——绝对值分布在关节限位区间内（比如 ±1.5），增量集中在零附近（比如 ±0.02）。**如果你把增量数据用绝对语义下发，机器人会瞬间冲到限位；反过来则几乎不动。** 这是最常见的「策略完全不工作」的原因。

**关节空间 vs 末端空间。** 关节空间直接对应硬件接口，不需要 IK，也不会有无解问题。末端空间和本体解耦，同一份数据理论上可以给不同机械臂用——这是 VLA 采用它的原因。代价是每一步都要跑 IK，而 IK 可能无解、可能在奇异点附近跳解（末端位姿连续变化但关节角突变），这类跳变在训练数据里会变成噪声。

**速度表示的特殊问题。** 任务开始前和结束后机器人静止，速度全是零。这些零帧在数据里占比可能很高，会让模型倾向于输出零动作（「不动」是损失最低的安全选择）。需要裁掉静止段或者加权。

**夹爪那一维单独说，因为它最容易错。** 三个必须确认的问题：

1. 二值还是连续？很多数据集里夹爪只有 0 和 1，模型输出 0.5 时你怎么解释？
2. 0 是张开还是闭合？LeRobot、ALOHA、OpenVLA 各家约定不同，甚至同一个仓库不同版本都变过。
3. 它的时序滞后有多大？夹爪从指令到实际闭合可能要 0.3 秒，也就是 10 帧。数据里 `action[6]` 从 0 跳到 1 那一帧，物体其实还没被夹住。

**必做：** 打开你的数据集，随便挑一帧，把这张表填完：

```
第 37 帧 action = [?, ?, ?, ?, ?, ?, ?]
维度 0-5: 什么物理量？什么单位？绝对还是增量？参考系是什么？
维度 6:   夹爪。二值还是连续？0 表示什么？
这一帧对应现实世界的第几秒？
```

答不上来就先别训练。

### 3.4 控制频率：把帧数换算成秒

控制频率是「每秒下发多少个动作」。它把数据集里的下标和现实世界的时间连起来。

```
控制频率 30Hz  →  一帧 = 33 毫秒
一条 200 帧的 episode = 6.7 秒
chunk_size = 100  →  一次预测覆盖 3.3 秒的动作
```

**为什么必须记住这个换算：** 超参数 `chunk_size` 的合理值完全由频率决定。同样 `chunk_size=100`，在 50Hz 下覆盖 2 秒（合理），在 500Hz 下覆盖 0.2 秒（等于退化成单步 BC），在 5Hz 下覆盖 20 秒（模型在预测整个任务，末端动作必然不准）。

频率选择的权衡：

- 太高（比如 1000Hz）：chunk 覆盖的实际时间太短，学不到长程结构；数据量爆炸；相邻帧的动作差异小于传感器噪声
- 太低（10Hz 以下）：动作不平滑，接触类任务会硬顶
- 真机常用 **30-50Hz**，这也是 ACT 和 LeRobot 的默认区间

**采集频率和训练频率可以不同。** 你可以用 50Hz 采，然后降采样到 25Hz 训练。但降采样时动作要跟着变：绝对表示直接抽帧就行，增量表示必须把被丢掉的帧的增量**累加**进保留帧，否则动作幅度会小一半。这个细节很多人漏掉。

**部署频率必须和训练频率一致。** 训练时 30Hz、部署时因为推理慢实际跑到 15Hz，策略的行为会和训练时不同——它以为自己每 33 毫秒动一次，实际是 66 毫秒。阶段 07 会讲怎么测量和修这个问题。

### 3.5 归一化：一个文件决定策略能不能用

神经网络对输入输出的数值范围敏感。关节角在 ±1.5 弧度，末端增量在 ±0.02 米，夹爪在 0-1——直接混着训练，梯度会被大范围的维度主导。

标准做法是按每个维度独立归一化：

```python
"""动作与状态的归一化统计量。

这个类的输出（一个 json 文件）是数据集的一部分，
必须和 checkpoint 一起保存、一起分发。

最常见的部署事故就是忘了加载它，或者加载了另一个数据集的统计量。
现象是机器人动作幅度差一个数量级——要么原地不动，要么冲向限位。
"""

from dataclasses import dataclass

import numpy as np


@dataclass
class ActionStats:
    """动作的归一化统计量。

    提供两种方案，用哪种取决于动作分布：

    mean/std（z-score）：适合近似正态的分布，比如关节角增量。
    q01/q99（分位数）：适合有离群值的分布。

    为什么用 1%/99% 分位数而不是 min/max：一次采集里手抖
    产生的极端动作会把范围拉宽，导致 99% 的常规动作全挤在
    归一化区间的中间一小段里，等效于损失了有效精度。
    """

    mean: np.ndarray
    std: np.ndarray
    q01: np.ndarray
    q99: np.ndarray

    @classmethod
    def fit(cls, actions: np.ndarray) -> "ActionStats":
        """从全部训练集动作计算统计量。

        注意：必须只用训练集，不能包含验证集。
        用了全量数据就是信息泄漏——虽然影响比分类任务小，
        但这个纪律不该破。
        """
        return cls(
            mean=actions.mean(axis=0),
            # 加 eps 防止某个维度全是常数时除零
            # （夹爪维度在只有二值的数据里很容易 std=0）
            std=actions.std(axis=0) + 1e-8,
            q01=np.percentile(actions, 1, axis=0),
            q99=np.percentile(actions, 99, axis=0),
        )

    def normalize(self, action: np.ndarray) -> np.ndarray:
        """训练时用：原始动作 -> 归一化动作。"""
        return (action - self.mean) / self.std

    def denormalize(self, normalized: np.ndarray) -> np.ndarray:
        """部署时用：模型输出 -> 可下发的动作。

        这一步漏掉是最高频的部署 bug。检查方法很简单：
        打印模型输出和反归一化后的值，看数量级是否符合
        你在 3.3 节确认过的动作语义。
        """
        return normalized * self.std + self.mean

    def sanity_check(self, raw_action: np.ndarray) -> list[str]:
        """检查一个原始动作是否在训练分布的合理范围内。

        部署时每一步都调用，超出范围就记录。
        如果大量超出，说明部署时的状态和训练分布差太远，
        这时策略输出已经不可信了——比让它继续执行安全。
        """
        warnings: list[str] = []
        below = raw_action < self.q01
        above = raw_action > self.q99
        for i in np.where(below | above)[0]:
            warnings.append(
                f"维度 {i} 的值 {raw_action[i]:.4f} 超出训练分布 "
                f"[{self.q01[i]:.4f}, {self.q99[i]:.4f}]"
            )
        return warnings
```

**图像的归一化单独一套。** 通常用 ImageNet 的 mean/std（因为视觉骨干是 ImageNet 预训练的）。这个不要自己改，改了预训练权重就白费了。

**三条纪律：**

1. 统计量文件和 checkpoint 放在同一个目录，一起版本化
2. 部署代码启动时打印统计量的 hash，确认加载的是对的那份
3. 每次重新采数据、扩充数据集，统计量都要重算

### 3.6 训练测试划分：按 episode 切，不按帧切

这一节短但重要，因为错法很有诱惑力。

**错的做法：** 把所有帧混在一起打乱，按 9:1 切分。

**为什么错：** 同一条 episode 里相邻帧几乎一样。这样切分后，验证集里每一帧在训练集里都有一个近乎相同的邻居，验证损失会低得离谱，而它什么都证明不了。

**对的做法：** 按 episode 划分。整条 episode 要么全在训练集，要么全在验证集。

```python
def split_episodes(
    episodes: list[Episode],
    val_ratio: float = 0.1,
    seed: int = 0,
) -> tuple[list[Episode], list[Episode]]:
    """按 episode 划分训练集和验证集。

    必须按 episode 切而不是按帧切：同一条轨迹的相邻帧
    高度相关，混在一起打乱会让验证集里出现训练集的近邻，
    验证损失虚低且失去意义。

    另一个容易漏的点：如果采集是分批做的（今天 20 条，
    明天 20 条），不同批之间可能有光照或摆放的系统差异。
    这时按批次划分（留一整批做验证）比随机划分更能反映泛化能力。
    """
    rng = np.random.default_rng(seed)
    indices = rng.permutation(len(episodes))
    n_val = max(1, int(len(episodes) * val_ratio))
    val_idx = set(indices[:n_val].tolist())

    train = [ep for i, ep in enumerate(episodes) if i not in val_idx]
    val = [ep for i, ep in enumerate(episodes) if i in val_idx]
    return train, val
```

**但更重要的一点在 3.11 节：** 对模仿学习来说，验证集本身的价值就有限。真正的评估必须在环境里实际跑。验证集主要用来发现「训练崩了」这种明显问题，不能用来选 checkpoint。

### 3.7 行为克隆：最朴素的做法

到这里数据部分讲完了。现在才开始讲模型——**顺序是刻意的，因为模型这部分你大概率已经会了。**

最朴素的模仿学习叫**行为克隆**（Behavior Cloning, BC）：把演示数据当成监督学习，输入观测，输出动作，最小化 MSE。

```python
"""最简单的行为克隆。

这个实现能跑，但会失败得很惨。理解它为什么失败，
比让它成功更重要——ACT 和 Diffusion Policy 的每个
设计决策都是在修这里的某个缺陷。
"""

import torch
import torch.nn as nn


class SimpleBCPolicy(nn.Module):
    """单步行为克隆：观测 -> 动作。

    刻意写得很朴素，用来演示 BC 的失败模式。
    真实项目不要用这个结构。
    """

    def __init__(self, obs_dim: int, action_dim: int, hidden: int = 256):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(obs_dim, hidden),
            nn.ReLU(),
            nn.Linear(hidden, hidden),
            nn.ReLU(),
            nn.Linear(hidden, action_dim),
        )

    def forward(self, obs: torch.Tensor) -> torch.Tensor:
        return self.net(obs)
```

BC 有两个根本缺陷，它们不是实现问题，是方法本身的问题。

**缺陷一：多模态动作分布。** 同一个观测下，人类演示可能有多种合理动作（绕左边走或绕右边走都行）。MSE 损失会让模型输出这些动作的平均值，而平均值往往是最糟的选择：

```
演示数据：有时向左 (-1)，有时向右 (+1)
MSE 最优解：0（正中间，撞上障碍物）
```

这个缺陷是 ACT 的 CVAE 和 Diffusion Policy 要解决的核心问题。

**缺陷二：分布偏移。** 单独一节讲，因为它更根本。

### 3.8 分布偏移：为什么 BC 一定会跑偏

训练时模型看到的是**专家轨迹上的状态**。部署时模型自己开车：

```
第 1 步：有个小误差，机器人到了一个专家没去过的位置
第 2 步：在这个陌生状态下预测得更差，误差变大
第 3 步：状态更陌生，预测更差
...
第 k 步：完全跑偏
```

这叫**复合误差**（compounding error），本质是**训练分布和部署分布不一致**——而这个不一致是策略自己造成的。这是模仿学习最核心的理论问题，经典处理方案叫 **DAgger**（让专家在模型犯错的状态下补充演示）。

结合 3.4 节的换算看这件事：30Hz 下一条 6 秒的轨迹是 180 次决策，每一次都在给下一次制造分布偏移的机会。

**三类缓解手段：**

| 手段 | 机制 | 代价 |
|---|---|---|
| 加噪训练 | 在观测里加噪声，迫使模型在偏离状态下也能预测 | 需要调噪声幅度 |
| 采集恢复行为 | 演示时故意偏一点再修正，教模型「偏了怎么办」 | 采集更累 |
| 动作分块 | 减少决策次数，从而减少误差累积的机会 | 见下节 |
| DAgger | 专家在模型的失败状态下补充演示 | 需要专家在环，成本高 |

**注意动作分块只是「减少累积次数」，不是消除分布偏移。** chunk 之间仍然会累积，而且 chunk 内部是开环执行的——这一段时间里策略完全不看反馈。这是一个真实的权衡，不是免费的收益。

### 3.9 动作分块：为什么它有效

**动作分块（action chunking）：** 不预测单步动作，一次预测未来 k 步（典型 k=100）。

三个收益：

1. **减少复合误差的累积次数。** 执行 100 步只需要 1 次预测，而不是 100 次
2. **隐式建模动作的时序连贯性**，避免逐帧预测导致的抖动
3. **缓解多模态问题。** 整段轨迹作为一个整体输出，不容易被平均成「向左和向右的中间」——因为「先向左的整条轨迹」和「先向右的整条轨迹」在输出空间里是两个远离的点，而不是两个可以取中点的标量

**时序集成（temporal ensembling）：** 每一步都重新预测一个 chunk，把多个 chunk 里对当前时刻的预测加权平均。这补回了 chunk 内开环执行丢掉的反馈能力——动作更平滑，同时保留高频反馈。代价是每步都要推理，延迟预算要求更高。

### 3.10 ACT 与 Diffusion Policy

**ACT（Action Chunking with Transformers）** 来自 ALOHA 论文，是目前真机操作最常用的基线之一。三个核心设计：动作分块、时序集成、以及用 CVAE 处理多模态（训练时编码器把演示动作压成隐变量 z，推理时从先验采样，让模型能表达多种可能动作而不是被迫输出平均值）。

```python
"""ACT 的核心结构示意。

这不是可运行的完整实现——直接用官方仓库或 LeRobot 的版本。
写在这里是为了让你理解它在做什么，读官方代码时不迷路。
"""

import torch
import torch.nn as nn


class ACTPolicySketch(nn.Module):
    """ACT 结构骨架。

    输入：多路相机图像 + 当前关节角度
    输出：未来 chunk_size 步的动作序列

    关键点是 forward 返回 (batch, chunk_size, action_dim)
    而不是 (batch, action_dim)。这一个维度的差别就是 ACT
    相对朴素 BC 的主要改进。

    注意 action_dim 的语义完全由你在 3.3 节的选择决定。
    这个类不知道也不关心那 7 个数字是绝对关节角还是末端增量——
    搞错了它照样训练收敛，只是部署时机器人会做出完全错误的动作。
    """

    def __init__(
        self,
        action_dim: int,
        chunk_size: int = 100,
        hidden_dim: int = 512,
        num_cameras: int = 2,
    ):
        super().__init__()
        self.chunk_size = chunk_size
        self.action_dim = action_dim

        # 每路相机一个视觉骨干（通常是 ResNet18，ImageNet 预训练）
        # TODO: 实际实现里用 torchvision.models.resnet18
        self.vision_backbones = nn.ModuleList()

        # 关节角度投影
        self.joint_proj = nn.Linear(action_dim, hidden_dim)

        # Transformer 编码器-解码器
        self.transformer = nn.Transformer(
            d_model=hidden_dim,
            nhead=8,
            num_encoder_layers=4,
            num_decoder_layers=7,
            batch_first=True,
        )

        # chunk_size 个可学习的查询 token，每个负责预测一步动作
        self.action_queries = nn.Parameter(torch.zeros(chunk_size, hidden_dim))

        self.action_head = nn.Linear(hidden_dim, action_dim)

        # CVAE 的隐变量维度
        self.latent_dim = 32

    def forward(
        self,
        images: torch.Tensor,
        joint_positions: torch.Tensor,
    ) -> torch.Tensor:
        """返回形状 (batch, chunk_size, action_dim) 的动作序列。"""
        raise NotImplementedError("用官方实现，这里只是结构说明")
```

**必读：** ACT 论文（ALOHA，"Learning Fine-Grained Bimanual Manipulation with Low-Cost Hardware"）。重点看 chunk_size 和 temporal ensembling 的消融实验，那部分告诉你这两个设计各贡献了多少。

**Diffusion Policy** 是另一条主流路线：把动作生成当成去噪过程，从纯噪声开始反复去噪，条件是当前观测。

| | ACT | Diffusion Policy |
|---|---|---|
| 多模态表达 | CVAE，中等 | 天然强，扩散模型本就擅长多模态 |
| 推理速度 | 快，单次前向 | 慢，需要多步去噪（可用 DDIM 加速） |
| 训练稳定性 | 较好 | 较好 |
| 实现复杂度 | 中 | 中高 |

实践中两者性能接近。任务的多模态性很强时（「把杯子放到桌上任意空位」）Diffusion Policy 通常更好。

**必读：** "Diffusion Policy: Visuomotor Policy Learning via Action Diffusion"。

**对你的建议：先只做 ACT。** 两个都做会拖长这个阶段，而 ACT 的坑更少、社区支持更好。

**ACT 的关键超参数，按重要性排序：**

| 参数 | 典型值 | 影响 |
|---|---|---|
| `chunk_size` | 100 | 太小退化成 BC，太大末端动作不准（结合 3.4 节换算成秒来判断） |
| 学习率 | 1e-5 ~ 1e-4 | 视觉骨干通常用更小的学习率 |
| batch size | 8 ~ 64 | 受显存限制，越大越稳 |
| 训练步数 | 50k ~ 200k | 看成功率曲线，不要看验证损失（下节说明） |
| KL 权重（CVAE） | 10 ~ 100 | 太小退化成确定性策略 |
| 图像增强 | 随机裁剪、色彩抖动 | 对真机泛化很重要 |

### 3.11 诚实评估

这一节是本阶段最重要的部分。

**先说一个必须知道的事实：验证损失和实际成功率的相关性很弱。**

这是模仿学习里最反直觉的一点。你的验证 MSE 从 0.02 降到 0.01，成功率可能完全没变，甚至下降。原因：

- MSE 衡量「和专家动作的平均差异」，但成功与否取决于关键时刻的精度，不是平均精度
- 抓取的成败可能只取决于最后几帧的 3 毫米，而这几帧在整条轨迹的 MSE 里权重极小

**所以唯一可信的指标是在环境里实际跑的成功率。** 每隔一段训练步数就跑 20-50 次评估，记录成功率曲线。

💡 联系你的经验：这就是代理指标 vs 真实指标的问题，和做 LLM 工具评测时遇到的一样——单个工具的调用成功率高，不代表端到端的回答质量好。这里的现象更极端。

具身领域的论文和 demo 视频普遍存在评估不严谨的问题。你从一开始就该建立正确的标准。

```python
"""策略评估：区分不同难度等级，记录失败模式。

这个类的设计目标是让「成功率 85%」这句话变得可核验：
在什么初始分布下、跑了多少次、失败的都是什么原因。
"""

from collections import Counter
from dataclasses import dataclass, field

import numpy as np


@dataclass
class EvalConfig:
    """评估配置。

    必须显式声明初始状态的随机化范围，因为成功率对它极度敏感。
    「85% 成功率」在 5cm 随机范围和 20cm 随机范围下是两个完全
    不同的结论。不写清范围的成功率数字没有意义。
    """

    num_episodes: int = 50
    position_randomization: float = 0.05  # 米
    rotation_randomization: float = 0.0   # 弧度
    distractor_objects: int = 0           # 干扰物数量
    lighting_variation: bool = False
    seed: int = 0

    def describe(self) -> str:
        """人类可读的配置描述，必须和成功率一起报告。"""
        return (
            f"{self.num_episodes} 次, "
            f"位置随机 ±{self.position_randomization * 100:.0f}cm, "
            f"旋转随机 ±{np.rad2deg(self.rotation_randomization):.0f}°, "
            f"干扰物 {self.distractor_objects} 个, "
            f"光照变化 {'有' if self.lighting_variation else '无'}"
        )


@dataclass
class EvalResult:
    """评估结果，包含失败模式分布。

    只报告成功率是不够的。失败模式的分布告诉你下一步该改什么：
    大量 grasp_slip 说明抓取姿态或夹爪力度有问题；
    大量 wrong_object 说明视觉部分没学好；
    大量 timeout 说明策略卡住了，可能陷入了某种循环。
    """

    config: EvalConfig
    successes: int
    failure_modes: Counter = field(default_factory=Counter)
    episode_lengths: list[int] = field(default_factory=list)

    @property
    def success_rate(self) -> float:
        return self.successes / self.config.num_episodes

    def report(self) -> str:
        lines = [
            f"成功率: {self.success_rate:.1%} ({self.successes}/{self.config.num_episodes})",
            f"评估条件: {self.config.describe()}",
        ]
        if self.failure_modes:
            lines.append("失败模式分布:")
            for mode, count in self.failure_modes.most_common():
                lines.append(f"  {mode}: {count}")
        if self.episode_lengths:
            lines.append(
                f"平均步数: {np.mean(self.episode_lengths):.1f} "
                f"(最短 {min(self.episode_lengths)}, 最长 {max(self.episode_lengths)})"
            )
        return "\n".join(lines)
```

**评估纪律，五条：**

1. **报告成功率必须附带随机化范围。** 不写范围的数字没有意义。
2. **评估次数至少 50 次。** 20 次的置信区间太宽——成功率 60% 和 75% 在 20 次样本下无法区分。
3. **分等级评估。** 至少三档：训练分布内、轻度分布外（更大随机范围）、重度分布外（加干扰物或改光照）。三个数字一起报告，才能看出泛化能力。
4. **记录失败模式。** 光知道失败率没用，要知道怎么失败的。
5. **固定随机种子并记录。** 否则你无法复现，也无法比较两个 checkpoint 的优劣。

💡 这套纪律和严谨的后端工程实践是同一个东西：区分本地、共享环境、生产三级验证证据，证据不足时拒绝声称完成。把这个习惯带进具身，你会比大部分同行更可信。

## 4. 最小实验

目标：**在一天之内看到一个能动的策略**，然后才谈优化。最短路径是用现成的仿真数据集，跳过采集。

**第一步：读一条别人的数据（30 分钟）。**

用 LeRobot 现成的仿真数据集（PushT 或 ALOHA 仿真任务），加载一条 episode，打印出来：

```python
"""数据契约体检脚本。

这是整个阶段的第一段代码，也是最该反复用的一段。
每次换数据集、换框架、换硬件，都重新跑一遍。
"""

import numpy as np


def inspect_episode(observations: list[dict], actions: np.ndarray, control_hz: float) -> None:
    """打印一条 episode 的数据契约，用来人工核对 3.3 / 3.4 节的问题。

    重点看三件事：
      1. 动作的数值范围——判断是绝对还是增量（绝对值大，增量集中在零附近）
      2. 相邻帧动作的差——判断控制频率是否合理（差异应该明显大于噪声）
      3. 夹爪维度的取值集合——判断是二值还是连续
    """
    print(f"帧数 {len(actions)}, 时长 {len(actions) / control_hz:.2f} 秒")
    print(f"观测字段: {list(observations[0].keys())}")
    print(f"动作维度: {actions.shape[1]}")
    for d in range(actions.shape[1]):
        col = actions[:, d]
        unique = np.unique(np.round(col, 3))
        print(
            f"  dim {d}: 范围 [{col.min():+.4f}, {col.max():+.4f}] "
            f"均值 {col.mean():+.4f} 相邻帧平均变化 {np.abs(np.diff(col)).mean():.5f} "
            f"取值数 {len(unique)}"
        )
```

**看这个输出你应该能自己判断出动作是绝对还是增量。** 均值接近零且范围很窄的是增量，均值明显偏离零且范围接近关节限位的是绝对值。「取值数」只有 2 或 3 的那一维就是夹爪。


先用默认超参数，不要调。目标不是好成绩，是确认整条链路通。

**第三步：跑一次评估（30 分钟）。**

```bash

```

看到一个非零的成功率就算通了。**这时你已经具备做后面所有实验的基础设施。**

采集的六个关键决定：

1. **初始状态随机化范围。** 从窄开始，训出能用的策略，再逐步扩大
2. **轨迹长度一致性。** 差异太大训练不稳定。如果专家有时 100 步有时 400 步，先修专家
3. **观测里放什么。** 图像加关节角，不放真值（3.2 节）
4. **动作表示。** 先用绝对关节角，最稳（3.3 节）
5. **控制频率。** 30Hz 起步（3.4 节）
6. **数据量。** 简单任务 50 条能看到效果，100-200 条到可用水平

## 5. 故障实验

跑通之后，故意把它弄坏。**这一节的价值大于第 4 节**——策略成功时你学不到什么，策略失败的方式才是知识。

每个实验都有明确的「观察什么」，做完记录在第 6 节的模板里。

**实验 1：动作错位一帧。**
把数据里的 actions 整体前移一帧（`actions[1:]` 配 `observations[:-1]`）重新训练。
**观察什么：** 训练损失几乎不变（这是重点，它不会报警）。成功率下降多少？失败时机器人的行为看起来像什么——是完全乱动，还是「慢半拍」？记住这个视觉特征，真机上你会用它来诊断。

**实验 2：不做反归一化。**
部署时跳过 `denormalize`，直接把模型输出下发。
**观察什么：** 机器人的动作幅度是什么量级？是原地不动还是冲向限位？这取决于你用的是绝对还是增量表示——两种都试一下，理解为什么表现相反。

**实验 3：用错的统计量。**
加载另一个数据集（或者只用前 10 条 episode 算出来）的 `ActionStats` 做反归一化。
**观察什么：** 现象和实验 2 的区别。这个更隐蔽——动作方向大致对，幅度系统性偏大或偏小。这正是 VLA 阶段 `unnorm_key` 选错的表现，提前见一次。

**实验 4：把物体真值塞进观测。**
故意把物体的真实位置加进 observation 重新训练。
**观察什么：** 训练分布内的成功率会涨（可能涨到 95% 以上）。然后把这个字段置零再评估，观察成功率崩到多少。这个对比就是数据泄漏的量化定义。

**实验 5：chunk_size 消融。**
试 1、10、50、100，画出成功率对 chunk_size 的曲线。
**观察什么：** `chunk_size=1` 就是 3.7 节的朴素 BC，它的失败模式是什么样（看是否符合 3.8 节描述的逐步跑偏）。曲线在哪里达到峰值？把峰值换算成秒，和任务的实际时长比一比。

**实验 6：改控制频率但不改 chunk_size。**
把数据降采样到 10Hz 重新训练，`chunk_size` 保持 100。
**观察什么：** 现在一个 chunk 覆盖 10 秒，超过了整个任务时长。策略实际上在预测整条轨迹，末端动作的精度会怎样？降采样时如果动作是增量表示，记得累加（3.4 节），不累加的话再观察一次动作幅度问题。

**实验 7：按帧划分验证集。**
把所有帧混起来打乱切分，观察验证损失。
**观察什么：** 验证损失比按 episode 划分低多少？成功率有变化吗？这个对比让你对「好看的验证指标」永久免疫。

**实验 8：验证损失 vs 成功率。**
把两条曲线画在同一张图上（横轴训练步数）。
**观察什么：** 相关性有多弱。找出验证损失最低的 checkpoint 和成功率最高的 checkpoint，看它们是不是同一个。这张图值得保留。

**实验 9：数据量消融。**
用 20、50、100 条数据分别训练。
**观察什么：** 成功率对数据量的曲线形状。在哪里开始饱和？失败模式随数据量增加是怎么变化的——是均匀下降还是某一类先消失？

**实验 10：只用成功轨迹 vs 混入失败轨迹。**
**观察什么：** 混入标记为失败的轨迹后成功率变化。这会告诉你 3.1 节「失败数据也要留」这条建议在你的具体设置下值多少。

## 7. 与 Agent / 后端的类比

模仿学习的整条流水线和你熟悉的机器学习工程几乎同构，几个对应关系可以直接搬：

**数据契约 = API schema。** 3.3 节那张动作表示的表，本质是一份接口定义。你在后端里绝不会容忍一个 `POST /orders` 的字段含义没写清楚，但很多人对自己的 action 向量就是这个状态。归一化统计量文件相当于 schema 的一部分，丢了它接口就对不上。

**训练/部署一致性 = 训练服务一致性（training-serving skew）。** 观测预处理、归一化、动作语义三处一致性，和特征工程里训练管道与在线管道必须一致是同一个问题。区别是这里的失败信号更弱：模型不会告诉你不一致，机器人只是乱动。

**验证损失 vs 成功率 = 代理指标 vs 业务指标。** 你在 LLM 评测里遇到的问题：单元测试全绿、工具调用成功率高，但端到端的回答质量没变。同一个陷阱，这里更极端。

**评估纪律 = 证据分级。** 「成功率 85%」不附随机化范围，等于在开发日志里写「已修复」不附验证证据。EvalConfig 存在的意义就是让这个数字可核验。

**分布偏移 = 反馈回路污染。** 模型自己的输出改变了它下一步的输入分布。这个结构你在推荐系统或者任何有反馈回路的线上系统里见过。

**失败模式分类 = 错误分类。** 你在 Agent 运行时里区分「工具不存在 / 参数错 / 上游超时 / 权限不足」，因为不同类型对应不同处理。这里的 `grasp_slip / wrong_object / timeout` 是同一件事，而且直接决定你下一步改数据、改标定还是改模型。

## 8. 这个类比在哪里失效

上面的类比能带你走很远，但有五个地方它会骗你。

**1. 没有可靠的单元测试等价物。** 后端里一个函数的正确性可以断言。这里没有：模型「正确」的唯一定义是在物理环境里跑出来的成功率，而这个数字有随机性，50 次评估的标准误差就有几个百分点。你无法写一个断言说「这个策略是对的」。CI 里能跑的只有形状检查和数据契约检查。

**2. 修一个 bug 不一定让指标变好。** 后端里修掉一个真 bug，行为一定更正确。这里你修掉一个数据错位，成功率可能不变甚至下降——因为模型已经学会了补偿那个错误，而你的其他超参数是围绕补偿后的行为调出来的。这让「逐个修问题」这种工程直觉失效，必须整体重训重评。

**3. 数据不是幂等的资源。** 后端里数据是可以重放、重算的。演示数据不是：你今天的手感、光照、桌面摆放不可复现。采完一批数据就固化了一段特定条件，扩充数据集时新旧批次之间会有系统差异（3.6 节提到的按批次划分就是因为这个）。你不能「重新采一份一样的数据」。

**4. 分布偏移不能靠幂等和重试解决。** 后端里请求失败重试一次通常就好了。策略跑偏之后，重试意味着从一个已经被改变的物理状态重新开始——物体位置变了，甚至掉到地上了。重试的前提「操作可安全重复执行」在这里不成立。这一点在阶段 08 会展开。

**5. 「训练服务一致性」的类比低估了严重性。** 特征不一致通常表现为准确率掉几个点，你能从监控上看出来。动作语义不一致的表现是机器人以最大速度冲向限位。同样是一致性问题，一个是指标退化，一个是硬件损坏。所以 3.5 节那三条纪律不是最佳实践，是硬性要求。
