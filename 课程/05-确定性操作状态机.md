# 阶段 05：确定性操作状态机

> 不用大模型，纯状态机跑通完整闭环 · 10-15 小时 · 无硬件要求

## 1. 为什么要学

这是整条路线里最容易被跳过、但最不该跳过的一个阶段。

你已经有了运动学（02）、轨迹与技能契约（03）、感知（04）。下一步的诱惑是直接上 LLM——毕竟你熟悉 tool calling，写个 agent 编排一下就能跑。

**但如果先上 LLM，你会失去归因能力。** 任务失败时，你分不清是感知定位偏了、IK 无解、轨迹撞了、夹爪没夹住，还是 LLM 决策错了。所有问题都会被笼统归结为「agent 不够聪明」，然后你开始调 prompt——而真正的问题可能在标定上。

这个阶段用一个**完全确定性的状态机**跑通同样的任务。没有大模型，没有不确定性，每一步都是你自己写的 if-else。跑通之后你会清楚地知道：

- 哪些问题属于感知
- 哪些属于 IK
- 哪些属于轨迹
- 哪些属于夹爪控制
- 哪些属于任务规划
- **哪些问题 LLM 根本不应该处理**

最后一条是本阶段最重要的产出。

## 3. 核心概念

### 3.1 完整的 pick-and-place 分解 `[MUST]`

先看任务的全貌。注意 verify 步骤，它们不是可选的：

```
OBSERVE            观测场景，定位目标
    ↓
APPROACH           移到物体上方 10cm（关节空间插值，快）
    ↓
DESCEND            垂直下降到抓取位姿（笛卡尔插值，慢）
    ↓
GRASP              闭合夹爪
    ↓
VERIFY_GRASP       ← 确认真的抓住了
    ↓
LIFT               抬升 15cm
    ↓
VERIFY_LIFTED      ← 确认物体跟着上来了
    ↓
TRANSFER           移到目标位置上方
    ↓
PLACE              下降并张开夹爪
    ↓
VERIFY_PLACED      ← 确认物体在目标位置
    ↓
RETREAT            撤离
    ↓
DONE
```

十二个状态里有三个是纯验证。这个比例不夸张——**在物理世界里，验证的代码量和执行的代码量应该是同一个量级。**

为什么 `VERIFY_LIFTED` 是独立的一步：夹爪可能夹住了物体但夹得不牢，抬升过程中滑落。只在 `VERIFY_GRASP` 检查是不够的。

### 3.2 「抓住了」怎么判断 `[MUST]`

这是本阶段最有价值的一个具体问题。有四种判据，每种都有漏洞：

| 判据 | 做法 | 漏报（以为没抓住） | 误报（以为抓住了） |
|---|---|---|---|
| **夹爪开度** | 闭合后夹爪没完全合并 | 物体很薄时判不出 | 夹到了别的东西（比如桌布） |
| **夹爪电流/力矩** | 闭合时遇到阻力 | 物体很软时力矩不明显 | 夹爪自己卡住了 |
| **视觉：物体消失** | 原位置看不到物体了 | 物体被手臂遮挡 | 物体被推走了而不是被抓走 |
| **视觉：抬升后物体跟随** | 抬起后物体位置也上升了 | 遮挡 | 几乎没有误报 |

```python
"""抓取成功的多判据校验。

单一判据都不可靠，所以用组合。但组合方式很重要——
用 AND 会让漏报率累加，用 OR 会让误报率累加。

这里的选择：先用便宜的判据快速排除明显失败（夹爪完全闭合
说明什么都没夹到），再用昂贵但可靠的判据确认（抬升后视觉复查）。
这是「快速失败 + 可靠确认」的组合。
"""

from dataclasses import dataclass


@dataclass
class GraspEvidence:
    """抓取成功的证据集合。

    每一项都可能是 None——传感器可能不存在，或者视觉被遮挡。
    None 表示「无信息」，不是「否」。这个区分很重要：
    把无信息当成否会导致大量误判失败。
    """

    gripper_gap: float | None = None          # 夹爪开度，米
    gripper_effort: float | None = None       # 夹爪力矩
    object_visible_at_origin: bool | None = None
    object_moved_with_gripper: bool | None = None

    def quick_reject(self, min_gap: float = 0.002) -> tuple[bool, str]:
        """快速排除：夹爪几乎完全闭合说明什么都没夹到。

        这个判据便宜（不需要视觉）且漏报少，适合做第一道筛。
        但它无法确认成功，只能确认失败。
        """
        if self.gripper_gap is not None and self.gripper_gap < min_gap:
            return True, f"夹爪开度 {self.gripper_gap:.4f}m 过小，未夹到物体"
        return False, ""

    def confirm(self) -> tuple[bool, str]:
        """可靠确认：抬升后物体是否跟着动了。

        这是唯一几乎没有误报的判据，但需要执行一次抬升，
        所以放在最后。
        """
        if self.object_moved_with_gripper is None:
            return False, "无法确认：视觉信息缺失"
        if self.object_moved_with_gripper:
            return True, "已确认抓住：抬升后物体随夹爪移动"
        return False, "未抓住：抬升后物体未随夹爪移动"
```

### 3.3 世界状态与 stale observation `[MUST]`

状态机需要记住「物体在哪」，但这个记忆会过期。

```python
"""带时效的世界状态。

核心设计：所有观测都带时间戳和有效期。
读取过期数据时必须显式失败，而不是静默返回旧值。

叫 belief 而不是 state，是为了持续提醒自己：
这只是「我相信的」，不是真值。
"""

import time
from dataclasses import dataclass, field

import numpy as np


@dataclass
class ObjectBelief:
    """对单个物体位置的信念。"""

    name: str
    position: np.ndarray
    observed_at: float
    valid_for: float = 3.0  # 秒

    def is_stale(self, now: float | None = None) -> bool:
        now = now if now is not None else time.monotonic()
        return (now - self.observed_at) > self.valid_for


@dataclass
class WorldBelief:
    """场景信念状态。

    invalidate 方法是这个类存在的核心理由：任何可能改变世界的
    动作之后必须调用它。让失效变成一个显式的、可审计的动作，
    比在每个读取点判断「这个数据还新鲜吗」要可靠得多。
    """

    objects: dict[str, ObjectBelief] = field(default_factory=dict)
    gripper_holding: str | None = None
    invalidated: bool = True  # 初始状态就是无效的，必须先观测

    def update(self, observations: dict[str, np.ndarray]) -> None:
        now = time.monotonic()
        self.objects = {
            name: ObjectBelief(name, pos, now)
            for name, pos in observations.items()
        }
        self.invalidated = False

    def invalidate(self, reason: str = "") -> None:
        """标记信念失效。在任何 world_changed 的动作后调用。"""
        self.invalidated = True

    def get_position(self, name: str) -> np.ndarray:
        """读取物体位置，过期或失效时抛异常。

        刻意抛异常而不是返回 None：这类错误应该在开发阶段
        就暴露出来，而不是让状态机拿着旧坐标继续跑。
        """
        if self.invalidated:
            raise StaleObservationError("信念已失效，必须重新观测")
        belief = self.objects.get(name)
        if belief is None:
            raise ObjectNotFoundError(f"物体 {name} 不在当前观测中")
        if belief.is_stale():
            raise StaleObservationError(
                f"{name} 的观测已过期 "
                f"({time.monotonic() - belief.observed_at:.1f}s)"
            )
        return belief.position.copy()


class StaleObservationError(RuntimeError):
    """观测过期。"""


class ObjectNotFoundError(RuntimeError):
    """物体未被观测到。"""
```

`invalidated` 初始值是 `True`——**状态机必须先观测才能做任何事**。这个默认值把「忘记观测」从一个隐蔽 bug 变成了一个立即失败。

### 3.4 失败的三种应对 `[MUST]`

不是所有失败都该重试。分三类：

| 类型 | 例子 | 应对 | 为什么 |
|---|---|---|---|
| **可原地重试** | 视觉这一帧没检测到物体 | 直接再试 | 世界没变，重试的初始条件相同 |
| **需重新观测后重试** | 抓取失败、碰倒了东西 | 先 invalidate，回到 OBSERVE | 世界已变，旧坐标无效 |
| **不可重试** | IK 无解、目标超出工作空间 | 放弃或换目标 | 重试一万次也是同样结果 |

```python
"""失败恢复策略。

关键设计是 max_attempts 按「同一个失败原因」计数，
而不是按总次数。这样「视觉丢帧 3 次然后抓取失败 1 次」
不会被误判为「已经失败 4 次该放弃了」。
"""

from collections import Counter
from enum import Enum


class RecoveryAction(str, Enum):
    RETRY_IN_PLACE = "retry_in_place"
    REOBSERVE_AND_RETRY = "reobserve_and_retry"
    ABORT = "abort"


# 失败原因 -> 恢复策略的静态映射。
# 显式列出所有已知失败原因，未列出的默认 ABORT——
# 宁可保守停下，也不要对未知失败盲目重试。
RECOVERY_POLICY: dict[str, RecoveryAction] = {
    "detection_missed": RecoveryAction.RETRY_IN_PLACE,
    "detection_low_confidence": RecoveryAction.RETRY_IN_PLACE,
    "grasp_failed": RecoveryAction.REOBSERVE_AND_RETRY,
    "object_slipped": RecoveryAction.REOBSERVE_AND_RETRY,
    "collision": RecoveryAction.REOBSERVE_AND_RETRY,
    "ik_unreachable": RecoveryAction.ABORT,
    "outside_workspace": RecoveryAction.ABORT,
    "joint_limit": RecoveryAction.ABORT,
}


class FailureTracker:
    """按原因分别计数失败次数。"""

    def __init__(self, max_attempts_per_reason: int = 3):
        self.counts: Counter[str] = Counter()
        self.max_attempts = max_attempts_per_reason

    def record(self, reason: str) -> RecoveryAction:
        """记录一次失败，返回该采取的恢复动作。"""
        self.counts[reason] += 1
        if self.counts[reason] >= self.max_attempts:
            return RecoveryAction.ABORT
        return RECOVERY_POLICY.get(reason, RecoveryAction.ABORT)

    def reset(self, reason: str | None = None) -> None:
        """成功后清除计数。"""
        if reason is None:
            self.counts.clear()
        else:
            self.counts.pop(reason, None)
```

### 3.5 状态机骨架 `[MUST]`

```python
"""确定性 pick-and-place 状态机。

刻意写成显式的状态枚举 + 转移函数，而不是一串顺序调用。
理由：顺序调用无法表达「失败后回到某个状态」，
而这恰恰是物理任务的常态。

TODO 留给你实现。照抄完整版学不到东西。
"""

from enum import Enum, auto


class State(Enum):
    OBSERVE = auto()
    APPROACH = auto()
    DESCEND = auto()
    GRASP = auto()
    VERIFY_GRASP = auto()
    LIFT = auto()
    VERIFY_LIFTED = auto()
    TRANSFER = auto()
    PLACE = auto()
    VERIFY_PLACED = auto()
    RETREAT = auto()
    DONE = auto()
    FAILED = auto()


class PickPlaceMachine:
    """确定性状态机。

    没有 LLM，没有随机性。每一步的决策都是你写死的规则。
    这是它的价值：任何失败都能精确归因到某个状态和某个判据。
    """

    def __init__(self, skills, perception, belief: WorldBelief):
        self.skills = skills
        self.perception = perception
        self.belief = belief
        self.tracker = FailureTracker()
        self.state = State.OBSERVE
        self.target_object: str | None = None
        self.place_target: np.ndarray | None = None
        self.history: list[tuple[State, str]] = []

    def step(self) -> State:
        """执行一个状态，返回下一个状态。

        每个状态的实现都要遵守两条：
          1. 只做一件事，做完就返回
          2. 失败时通过 tracker 决定去哪，不要自己 continue 重试
        """
        handler = getattr(self, f"_on_{self.state.name.lower()}", None)
        if handler is None:
            raise NotImplementedError(f"状态 {self.state} 未实现")
        next_state = handler()
        self.history.append((self.state, next_state.name))
        self.state = next_state
        return next_state

    def run(self, max_steps: int = 100) -> bool:
        """跑到终态。返回是否成功。"""
        for _ in range(max_steps):
            if self.state in (State.DONE, State.FAILED):
                break
            self.step()
        return self.state == State.DONE

    def _on_observe(self) -> State:
        """观测场景，刷新信念。"""
        observations = self.perception.observe()
        if not observations:
            action = self.tracker.record("detection_missed")
            return State.FAILED if action == RecoveryAction.ABORT else State.OBSERVE
        self.belief.update(observations)
        self.tracker.reset("detection_missed")
        return State.APPROACH

    def _on_approach(self) -> State:
        """移到物体上方。

        TODO:
          1. 从 belief 读目标位置（注意可能抛 StaleObservationError）
          2. 算出上方 10cm 的位姿
          3. 调 skills.move_to（关节空间插值即可，这段不需要直线）
          4. 失败时用 tracker 决定下一步
        """
        raise NotImplementedError

    def _on_descend(self) -> State:
        """垂直下降到抓取位姿。

        TODO: 必须用笛卡尔插值，否则夹爪会斜着切进去推倒物体。
        这是阶段 03 故障实验 C 的直接应用。
        """
        raise NotImplementedError

    def _on_verify_grasp(self) -> State:
        """校验是否抓住。

        TODO:
          1. 收集 GraspEvidence
          2. 先 quick_reject
          3. 通过则进 LIFT（真正的确认在 VERIFY_LIFTED）
        """
        raise NotImplementedError

    def _on_verify_lifted(self) -> State:
        """抬升后确认物体跟随。

        TODO:
          1. 重新观测（关键：不能用抬升前的信念）
          2. 检查物体位置是否也上升了
          3. 失败说明滑落，invalidate 后回 OBSERVE
        """
        raise NotImplementedError
```

## 5. 故障实验

### 故障 1：去掉所有 VERIFY 状态

把三个验证状态直接短路（永远返回下一步）。

**观察什么**：状态机会在没抓到东西的情况下继续执行 TRANSFER 和 PLACE，最后「成功」地把空气放到目标位置，并报告 DONE。

**这是本阶段最重要的一个实验。** 它演示了什么叫静默失败：系统报告成功，实际什么都没做成。而且注意——如果你只看最终的 `run()` 返回值，你根本发现不了。

### 故障 2：去掉 invalidate

抓取失败后不调用 `belief.invalidate()`，直接回到 APPROACH。

**观察什么**：状态机拿着抓取前的旧坐标去抓——但物体已经被推歪了。它会反复在同一个错误位置尝试，每次都失败在同一个地方。

### 故障 3：把 valid_for 设成很大

把 `ObjectBelief.valid_for` 改成 3600 秒。

**观察什么**：过期检测形同虚设。配合手动干扰（实验见故障 5）会产生完全错误的行为。

### 故障 4：所有失败都原地重试

把 `RECOVERY_POLICY` 全部改成 `RETRY_IN_PLACE`。

**观察什么**：`ik_unreachable` 这类永久性失败会被重试到次数上限，浪费时间。反过来把全部改成 `ABORT`，则一次视觉丢帧就会让整个任务失败。这两个极端说明了为什么必须分类。

### 故障 5：执行中手动改变世界

在 TRANSFER 状态时，手动把目标放置位置的坐标改掉（或者在仿真里移动一个障碍物）。

**观察什么**：状态机毫无察觉。它没有「有人动了东西」的检测机制。

**这个实验引出阶段 10 的一个核心问题**：外部干扰的检测。注意这不是 LLM 能解决的——LLM 也只能看到你给它的观测。这是运行时的职责。

### 故障 6：降低验证的容差

把 `VERIFY_PLACED` 的位置容差从 3cm 改成 3mm。

**观察什么**：大量误报失败——物体明明放好了，但因为定位噪声导致判定不通过。反过来改成 20cm，则物体掉在桌上也会被判成功。

**这个实验说明**：容差没有正确答案，你必须自己在漏报和误报之间选一个平衡点，而这个选择依赖具体任务的要求。

## 7. 与 Agent / 后端的类比

**状态机 ↔ 工作流引擎。** 显式状态、转移函数、终态，这和后端的订单状态机、审批流是同一个结构。

**stale observation ↔ 缓存失效。** `valid_for` 就是 TTL，`invalidate()` 就是主动失效。而且这里是最难的那种缓存问题：数据源不提供变更通知，你只能靠 TTL 加主动失效兜底。

**失败分类 ↔ 错误分类重试。** 可原地重试对应「网络抖动，重试即可」；需重新观测对应「乐观锁冲突，重读后再试」；不可重试对应「参数非法，重试无意义」。这套分类你在后端已经做过。

**FailureTracker 按原因计数 ↔ 分类熔断。** 不该因为「下游超时 3 次」就把「参数错误」也算进同一个熔断计数器。

**后置校验 ↔ 写后读校验。** 「写完再读一遍确认真的写进去了」，在物理世界里变成「动作完成后观测确认状态真的变了」。

## 8. 这个类比在哪里失效

**「状态机就是工作流引擎」失效在状态的存放位置上。** 后端状态机的状态在数据库里——你写入 `status='shipped'`，它就是 shipped，读出来永远一致。物理状态机的真实状态**在世界里**，你的枚举变量只是一个猜测。`self.state == State.LIFT` 不代表物体真的被举起来了。这是最根本的差异，也是为什么需要三个 VERIFY 状态。

**「stale observation 就是缓存失效」失效在三个点上：**

1. 后端缓存失效后重读能拿到真值，物理世界重新观测拿到的仍然是带噪声的估计。你无法通过「再读一次」获得确定性。
2. 后端缓存失效的原因通常是「有人改了数据」，而物理世界的状态会**自己变化**——物体会滑落、会因为惯性继续移动、会被重力拉倒。没有任何写操作，状态也在变。
3. 后端的缓存失效是幂等的：失效两次和失效一次一样。而物理世界里「重新观测」这个动作本身可能需要移动机器人（换视角），而移动可能改变场景。**观测行为本身有副作用。**

**「错误分类重试」失效在重试的语义上。** 后端的重试是「再发一次同样的请求」——请求内容不变，世界状态不变。物理世界的「重试抓取」中，物体位置已经变了，所以这不是重试，**是一个针对新初始条件的新动作**。把它叫重试会让你误以为初始条件相同。

**「写后读校验」失效在容差上。** 后端的校验是精确的：读出来的值等于写进去的值。物理校验必须带容差，而容差的选择直接决定漏报率和误报率——故障实验 6 就是在演示这件事。没有哪个容差是「正确」的。

**一个后端里完全不存在的问题：** 外部干扰（故障实验 5）。后端系统里，除了你的写操作没人能改数据；物理世界里，人可以随时拿走物体。你的状态机必须能容忍「世界在我不知情的时候变了」这件事，而这在后端里几乎不需要考虑。
