## 1. 为什么要学

前面的阶段都在仿真里。仿真是干净的：观测无噪声、执行精确、时间可以暂停、失败可以重置。

真机全部相反。

在整个具身系统里，这一层是所有上层设计的现实检验。阶段 05 讲的动作语义、阶段 06 讲的延迟预算，在仿真里都是抽象的数字；到真机上它们变成具体的失败现象。**你在这里学到的最重要的东西是一套归因方法**——面对「机械臂擦着方块过去了」这个现象，怎么系统地定位是硬件、标定、感知还是策略的问题。这套方法在纯仿真环境里学不到，因为仿真里下面三层永远是对的。

这也是为什么这一节的价值大于「我让真机动起来了」这个成就。

## 2. 学完后必须能回答

- 你的机械臂单关节重复定位精度是多少度？这个误差经过连杆放大后，末端偏差是多少毫米？
- 给一个固定角度指令，实际到位值和指令值差多少？这个差是系统性的还是随机的？怎么区分？
- 你的端到端控制循环里，图像采集、推理、通信下发各占多少毫秒？哪一段最大？
- 训练时的动作是什么语义，部署时下发的是什么语义？你怎么验证它们一致？
- 策略失败时，你的排查顺序是什么？为什么不能从策略开始查？
- 舵机堵转会发生什么？你怎么在它损坏之前发现？
- 软件限位和机械限位的关系是什么？为什么要留余量？

### 3.2 标定：所有归因困难的根源

组装跟着官方文档走。这里只说容易出问题、且换硬件也不变的地方。

**舵机 ID 设置。** 每个舵机出厂 ID 相同，必须逐个改成不同 ID。这一步顺序错了后面全乱。贴标签。

**零位标定。** 每个关节的「0 度」在哪，需要手动摆到中位然后写入。零位偏了会导致所有 IK 计算**系统性偏差**——所有动作朝同一个方向偏同样的量。

**关节方向。** 舵机的正方向和你的运动学模型假设的正方向可能相反。检查方法：给一个小的正向指令，看关节朝哪边动。

**限位。** 软件限位必须设在机械限位内侧（留 5 度余量），否则舵机会撞到机械结构造成堵转，堵转会持续发热并损坏舵机。

**系统偏差和随机噪声怎么区分——这是标定阶段最重要的一个判据：**

```
反复给同一个指令 10 次，测量实际到位值：
  均值偏离指令值  →  系统偏差  →  标定问题
  方差大          →  随机噪声  →  硬件精度问题（回差、松动）
两者都有          →  先修标定，噪声修不了只能接受
```

**这个区分决定你接下来是重新标定还是接受精度上限。** 搞混了会让你反复重训策略而问题从来不在策略。

### 3.3 安全：五条纪律

真机会伤人和自伤。低成本机械臂力量不大，但仍需要基本纪律。

1. **物理急停可达。** 手边有电源开关或急停按钮，能一秒切断。**软件的停止指令在程序卡死时无效**——这是必须有物理开关的全部理由
2. **限制速度。** 开发阶段把速度上限设到很低（正常速度的 30%）。快速运动是大部分事故的原因
3. **工作区清空。** 机器人周围不放水杯、不放手机、不放你的手
4. **先空跑。** 任何新策略先在没有物体的场景里跑一遍，确认轨迹不会撞到自己或桌面
5. **过流保护。** 舵机堵转会持续发热。监控电流和温度，异常时立刻断电

**舵机温度和电流单独说，因为它是最容易忽略的损坏原因。**

堵转（关节想动但被挡住）时舵机会持续加大电流试图到位，电能全部转成热。表现是：外壳发烫、电流读数居高不下、关节位置不变。这个状态持续几分钟就足以损坏舵机。**常见的触发场景不是撞击，是「举着东西等待」**——比如阶段 08 的 HITL 挂起，如果机器人举着重物等人回答，舵机会一直在承重发热。这就是为什么挂起前必须先放下物体。

```python
"""真机安全包装层。

这一层的存在意义是：即使上层策略输出了危险指令，
这里也能拦住。永远不要信任策略的输出——阶段 06 的实验 3
已经证明它对任何输入都会给出一个动作。
"""

import numpy as np


class SafetyLimiter:
    """动作安全限制器。

    这是一个纯函数式的过滤层，放在策略和硬件之间。
    它不关心策略为什么输出这个动作，只负责保证下发到
    硬件的指令在安全范围内。

    设计原则：宁可让任务失败，不可让硬件受损。
    """

    def __init__(
        self,
        joint_limits: np.ndarray,      # (n, 2) 每个关节的 [min, max]
        max_velocity: np.ndarray,       # (n,) 每步最大变化量
        workspace_bounds: np.ndarray,   # (3, 2) 末端可达空间的 xyz 范围
    ):
        self.joint_limits = joint_limits
        self.max_velocity = max_velocity
        self.workspace_bounds = workspace_bounds

    def limit(
        self,
        target_joints: np.ndarray,
        current_joints: np.ndarray,
    ) -> tuple[np.ndarray, list[str]]:
        """限制目标关节角度到安全范围。

        返回 (安全的目标角度, 触发的限制列表)。

        触发列表不能忽略——如果每一步都在触发限速，
        说明策略输出的动作幅度和你的限制不匹配，
        这时策略实际执行的是被削弱的版本，行为会和训练时不同。
        这种情况下调策略是白费力气，要先解决幅度不匹配。
        """
        triggered: list[str] = []
        safe = target_joints.copy()

        # 1. 关节限位
        clipped = np.clip(safe, self.joint_limits[:, 0], self.joint_limits[:, 1])
        if not np.allclose(clipped, safe):
            triggered.append("joint_limit")
            safe = clipped

        # 2. 速度限制：限制单步变化量
        delta = safe - current_joints
        excessive = np.abs(delta) > self.max_velocity
        if excessive.any():
            triggered.append("velocity_limit")
            delta = np.clip(delta, -self.max_velocity, self.max_velocity)
            safe = current_joints + delta

        return safe, triggered
```

💡 联系你的经验：这就是 AgentTrust Runtime 里做的事——在工具执行前做权限和边界检查，不信任上游的输出。区别是这里的后果是物理性的。阶段 08 会把这个类比推到底。

### 3.4 数据采集与 replay

leader-follower 设计的采集方式：你手动操作 leader 臂，follower 臂跟随，同时记录两者的关节角度和相机图像。

```bash
# 采集命令（示意，以框架当前版本文档为准）
lerobot-record \
  --robot.type=so101_follower \
  --teleop.type=so101_leader \
  --dataset.repo_id=你的用户名/pick_block \
  --dataset.num_episodes=50 \
  --dataset.single_task="pick up the red block"
```

> ⚠️ 需核实：LeRobot 的 CLI 命令和参数名变化频繁，务必先看官方 README。

**采数据的实践要点，这些比代码重要：**

**保持动作风格一致。** 同一个任务，每次的接近路径、速度、抓取姿态尽量一致。风格混乱的数据会让模型学到平均行为——这就是阶段 05 讲的多模态问题在真机上的表现。

**故意包含恢复行为。** 只采完美轨迹会让模型没有纠错能力（阶段 05 的分布偏移）。做法：偶尔故意偏一点，然后修正回来。这些数据教会模型「偏了怎么办」。

**随机化初始位置。** 每条轨迹开始前把物体放在不同位置。范围先小（±5cm），后面可以扩大。

**记录失败。** 采集时如果失败了，不要直接删。标记为失败保留下来，训练时再决定是否用。采集是不可逆的，过滤是可逆的。

**分批采集。** 一次采 50 条会很累，累了动作质量下降。分几次采，每次 15-20 条。注意批次之间可能有光照或摆放的系统差异（阶段 05 第 3.6 节提过按批次划分验证集的理由）。

**手腕会酸。** 这不是玩笑。50 条演示大概一小时，全程手臂悬空操作 leader。安排好休息。

**replay：采完必须回放。**

回放是验证数据链路正确的唯一手段，而且它能在训练之前就抓出错误。做法：把采集的动作序列原样重新下发给机器人，不经过任何模型。

```python
"""数据回放：在训练之前验证数据链路。

回放能在花几小时训练之前抓出三类致命问题：
  1. 动作语义错误（绝对/增量搞混）——回放时机器人乱动或不动
  2. 对齐错位——回放的轨迹比原始演示「慢半拍」
  3. 丢帧——回放时动作出现跳跃

这三类问题在训练时都不会报错，只会让成功率无声地下降。
花十分钟回放，能省下几天的排查。
"""

import numpy as np


def replay_episode(
    robot,
    safety: "SafetyLimiter",
    actions: np.ndarray,
    control_hz: float,
    *,
    dry_run: bool = True,
) -> dict:
    """回放一条采集的轨迹。

    dry_run=True 时只做安全检查和统计，不真的下发指令。
    第一次回放一定要先 dry_run——如果动作语义搞错了，
    直接下发会让机器人冲向限位。

    返回的 safety_triggers 是关键指标：采集数据的回放
    本应完全不触发任何安全限制（因为它来自真实的物理运动）。
    如果触发了，说明数据链路某处变换错了。
    """
    stats = {"steps": len(actions), "safety_triggers": [], "max_delta": 0.0}

    for i, action in enumerate(actions):
        current = robot.read_joint_positions()
        safe, triggered = safety.limit(action, current)
        if triggered:
            stats["safety_triggers"].append((i, triggered))

        stats["max_delta"] = max(stats["max_delta"], float(np.abs(action - current).max()))

        if not dry_run:
            robot.set_joint_positions(safe)
            # TODO: 按 control_hz 维持节拍，用 3.5 节的 RealtimeController

    return stats
```

**回放通过的判据：** 零安全触发，且肉眼看轨迹和你当时的演示一致。任何一条不满足，先修数据链路再训练。

### 3.5 控制频率、通信延迟与部署一致性

训练完成后部署。真机推理循环和仿真的最大区别是**它必须实时**。

```python
"""真机推理循环。

关键差异：仿真里你控制时间（mj_step 推进），真机上时间自己走。
如果你的推理比控制周期慢，就会累积延迟，机器人动作变得迟滞。
"""

import time

import numpy as np


class RealtimeController:
    """固定频率的真机控制循环。

    维护一个固定的控制周期，并监控实际耗时。
    超时不是可以忽略的警告——它意味着策略实际运行在
    比训练时更低的频率上，行为会不一致（阶段 05 第 3.4 节）。
    """

    def __init__(
        self,
        policy,
        robot,
        camera,
        safety: SafetyLimiter,
        control_hz: float = 30.0,
    ):
        self.policy = policy
        self.robot = robot
        self.camera = camera
        self.safety = safety
        self.period = 1.0 / control_hz
        self.overrun_count = 0

    def run(self, instruction: str, max_steps: int = 300) -> dict:
        """执行一个任务，返回统计信息。"""
        stats = {"steps": 0, "overruns": 0, "safety_triggers": []}

        for step in range(max_steps):
            loop_start = time.perf_counter()

            # 1. 观测
            image = self.camera.read()
            current_joints = self.robot.read_joint_positions()

            # 2. 策略推理
            target_joints = self.policy.predict(image, current_joints, instruction)

            # 3. 安全过滤（永远不要跳过这一步）
            safe_joints, triggered = self.safety.limit(target_joints, current_joints)
            if triggered:
                stats["safety_triggers"].extend(triggered)

            # 4. 下发
            self.robot.set_joint_positions(safe_joints)

            stats["steps"] = step + 1

            # 5. 维持固定频率
            elapsed = time.perf_counter() - loop_start
            remaining = self.period - elapsed
            if remaining > 0:
                time.sleep(remaining)
            else:
                # 超时了：这一步实际耗时超过控制周期
                self.overrun_count += 1
                stats["overruns"] = self.overrun_count

        return stats
```

**延迟来自哪几段，必须逐段测量：**

| 段 | 典型量级 | 说明 |
|---|---|---|
| 图像采集 | 10-50ms | USB 相机的曝光加传输，经常是最大的一段 |
| 图像预处理 | 1-5ms | resize、归一化 |
| 策略推理 | ACT 几毫秒；VLA 几十到上百毫秒 | 阶段 06 第 3.8 节 |
| 通信下发 | 5-20ms | 串口或 USB 到舵机 |
| 舵机响应 | 几十毫秒 | 这段你控制不了，但它存在 |

**很多人只测推理，然后困惑为什么循环跑不到 30Hz。** 图像采集和通信加起来经常比推理大。

**部署时必查的三件一致性：**

**1. 推理延迟满足控制周期。** 30Hz 意味着每步 33 毫秒预算，其中要包含上表所有段。先测量再优化。

**2. 观测的预处理必须和训练时完全一致。** 图像尺寸、归一化参数、通道顺序（RGB vs BGR）、裁剪方式。这里错一点策略就完全不工作。这是真机部署最高频的 bug。

**3. 动作的语义必须一致。** 训练时用的是绝对关节角度还是增量？角度单位是弧度还是度？夹爪的 0 是张开还是闭合？——这就是阶段 05 第 3.3 节那张表，在这里要拿着 checkpoint 和硬件驱动的文档逐维核对一遍。

💡 联系你的经验：这三条本质是训练服务一致性问题，和模型部署里的特征不一致是同一类问题。区别是这里的表现是机器人乱动，而不是准确率下降。

### 3.6 相机位置：最便宜的调优旋钮

相机的位置和视角对策略的影响，经常大于任何超参数。

三个具体点：

**1. 视角必须能看到关键信息。** 顶部相机看得到物体位置但看不到夹爪和物体的接触关系。腕部相机反过来。抓取任务通常两个都要。

**2. 相机位置一旦确定就不能动。** 采完数据之后碰了一下相机，整个数据集就废了一部分——策略学的是「这个视角下的这个像素位置对应那个空间位置」。用支架固定，别用夹子。

**3. 如果用预训练模型，把相机摆到接近预训练数据集的视角。** 这是 domain adaptation 里最便宜的手段（阶段 06 第 3.9 节），零算法成本，只是摆放的功夫。

**光照也算在这一节里。** 固定光源，不要靠窗（一天里的自然光变化足以让策略失效）。这是「换了个时间跑就不成功了」这类玄学现象的最常见原因。

### 3.7 sim2real 落差的来源

如果你想把仿真训的策略搬到真机，需要知道差异来自哪里。按影响大小排序：

**1. 视觉外观差异（影响最大）。** 仿真渲染和真实相机图像差别巨大：光照模型、纹理、噪声、镜头畸变、白平衡。这是 sim2real 失败的首要原因。

**2. 动力学差异。** 摩擦系数、关节阻尼、舵机响应曲线、连杆柔性。仿真里的刚体假设在真机上不成立——3D 打印件会弯。

**3. 延迟。** 真机有通信延迟、图像采集延迟、舵机响应延迟，加起来可能几十毫秒。仿真里是零。策略训练时看到的是「当前」图像，真机上看到的是「几十毫秒前」的图像。

**4. 标定误差。** 相机内外参、零位偏移。这是系统偏差，会让所有动作一致地偏。

**5. 物体差异。** 仿真里的方块是完美立方体，真实方块有倒角、有重心偏移、表面摩擦不均。

**主流应对手段：**

| 手段 | 针对 | 说明 |
|---|---|---|
| 域随机化 | 视觉、动力学 | 训练时随机化光照、纹理、摩擦、质量，让策略被迫鲁棒 |
| 真实图像增强 | 视觉 | 加噪声、模糊、色彩抖动，模拟真实相机 |
| 系统辨识 | 动力学 | 测量真机参数，调仿真参数去匹配 |
| 延迟建模 | 延迟 | 在仿真里人为加入和真机匹配的延迟 |
| 真机数据微调 | 全部 | 最有效，也最省事 |

**对你的建议：跳过 sim2real，直接在真机上采数据训练。**

理由很实际：sim2real 是一个独立的研究课题，投入产出比对你不划算。而低成本机械臂采 50 条数据只要一小时，直接真机训练又快又有效。

sim2real 真正有价值的场景是「真机数据极其昂贵或危险」（自动驾驶、腿足机器人摔倒）。桌面机械臂不属于这一类。

### 3.8 分层调试方法论

真机不给 stack trace。策略失败了，你面对的是「机械臂擦着方块过去了」这个现象，需要自己定位原因。

**建立分层排查顺序，从下往上：**

**第 0 层：硬件。** 舵机是否正常响应？给一个固定角度指令，实际到位精度多少？重复 10 次的一致性如何？如果这一层就有问题（比如某个舵机有 3 度回差），上层怎么调都没用。

**第 1 层：标定。** 用手动遥操作把夹爪对准一个已知位置的物体，读出关节角度，用 FK 算出末端位置，和实际测量对比。偏差多少？方向一致吗？如果是一致的偏差，就是标定问题（3.2 节的系统偏差判据）。

**第 2 层：感知。** 相机看到的物体位置和实际位置差多少？把物体放在几个已知位置，逐个验证。

**第 3 层：策略。** 前三层都确认没问题，再怀疑策略。这时的排查手段是回放训练数据看模型在训练分布内的表现，以及可视化模型的注意力。

**这个顺序不能颠倒。** 大部分人的错误是直接怀疑策略、反复重训，而问题其实在标定。**上层的表现会被下层的问题污染**——在一个零位偏 2 度的机械臂上，无论你怎么调策略都得不到干净的信号。

```python
"""分层诊断工具。

每一层都有一个可量化的判据。写下来，因为真机调试时
很容易凭感觉判断，而感觉不可靠。
"""

from dataclasses import dataclass


@dataclass
class DiagnosticReport:
    """分层诊断结果。

    按 layer 从低到高排查，第一个不通过的层就是问题所在。
    不要跳层——上层的表现会被下层的问题污染。
    """

    layer: str
    passed: bool
    measured_value: float
    threshold: float
    unit: str
    note: str = ""

    def describe(self) -> str:
        status = "通过" if self.passed else "不通过"
        return (
            f"[{self.layer}] {status}: "
            f"实测 {self.measured_value:.4f}{self.unit} "
            f"(阈值 {self.threshold:.4f}{self.unit}) {self.note}"

    统计标准差。舵机的回差（backlash）会在这里暴露。

    阈值 0.5 度是经验值：超过这个数，末端位置误差会
    大到影响抓取——关节误差经过连杆放大，0.5 度在
    30 厘米臂长处约是 2.6 毫米。

    注意这里测的是标准差（随机噪声），均值偏离测的是
```

## 4. 最小实验

**目标：不训练任何模型，先证明整条硬件链路是对的。** 这个顺序很重要——在链路没验证的硬件上采数据是纯浪费。

**第一步：标定与第 0 层诊断（半天到一天）。**

1. 舵机 ID 逐个设好并贴标签
2. 零位标定，逐关节验证
3. 关节方向验证（正向指令看动的方向）
4. 软件限位设在机械限位内侧 5 度
5. 跑 `diagnose_joint_repeatability`，每个关节重复精度 < 0.5 度
6. 记录每个关节的系统偏差（均值偏离）和随机噪声（标准差），分开记

**通不过就不要往下走。** 这条纪律会救你几天时间。

**第二步：接上 SafetyLimiter（1 小时）。**

实现 `SafetyLimiter`，接到**所有**下发路径上，然后故意给它一个越界指令，确认它拦住了。这一步在采数据之前做，因为遥操作也可能产生越界动作。

**第三步：测量延迟（1 小时）。**

按 3.5 节那张表逐段测量，填出你自己的数字：

```
图像采集      ___ ms
图像预处理    ___ ms
策略推理      ___ ms（先用一个随机策略占位）
通信下发      ___ ms
端到端        ___ ms  →  最高频率 ___ Hz
```

**这五个数字决定了你的控制频率上限**，而控制频率决定了采集频率（两者必须一致）。

**第四步：采 10 条数据并回放（2 小时）。**

先只采 10 条，然后：

1. `replay_episode(dry_run=True)` — 确认零安全触发
2. `replay_episode(dry_run=False)` — 肉眼确认轨迹和演示一致
3. 用阶段 05 的 `inspect_episode` 打印动作契约，确认语义

**三项都过了，再采剩下的 40 条。** 这是本节最省时间的一条建议。

**第五步：训练与部署（一天）。**

1. 训 ACT（用阶段 05 的流程）
2. 部署，用 `RealtimeController`，记录 overrun 次数
3. 空跑一次（场景里不放物体），确认轨迹不撞
4. 评估 30 次，统计成功率和失败模式

**预期结果：第一次训练成功率 30-50%。** 改进一轮后 60-80%。如果第一次就超过 80%，检查一下任务是不是设计得太简单（比如物体位置几乎不变）。

**改进的常见方向，按性价比排序：**

1. 补数据。失败集中在某类初始位置？针对那个区域多采 20 条
2. 查标定。系统性偏一个方向就是标定问题
3. 调相机位置和光照。零算法成本（3.6 节）
4. 加图像增强。光照变化导致失败就加色彩抖动重训
5. 调 chunk_size。动作不平滑或末端不准可以试
6. 换策略架构。最后手段，通常收益最小

## 5. 故障实验

**标注了「仿真可做」的实验不需要硬件**——如果你没买硬件，把这几个在 MuJoCo 里做掉，能拿到这一节大部分的认知收益。

**实验 1：注入延迟（仿真可做）。**
在仿真的观测路径上人为延迟 2-3 帧（用一个 deque 缓存旧观测），重新评估已训好的策略。
**观察什么：** 成功率下降多少。策略的行为特征是什么——是「慢半拍」还是振荡？延迟到多少帧时策略完全失效？这个数字就是你的延迟预算上限。

**实验 2：训练与部署频率不一致（仿真可做）。**
30Hz 训练的策略，部署时跑 15Hz。
**观察什么：** 动作变得迟滞还是幅度不对？（取决于动作是绝对还是增量表示，两种都试）这正是 overrun 累积后的实际后果。

**实验 3：动作语义错位（仿真可做）。**
把增量表示的策略输出按绝对语义下发，或者反过来。**在仿真里做，不要在真机上做**——真机上这个实验会撞坏东西。
**观察什么：** 两个方向的现象差异（一个冲限位，一个几乎不动）。记住这两种视觉特征，真机上你会靠它们诊断。

**实验 4：改变通道顺序（仿真可做）。**
部署时把图像的 RGB 换成 BGR。
**观察什么：** 策略是完全失效还是部分工作？如果任务里颜色是关键判据（抓红块不抓蓝块），观察它是不是系统性地抓错了颜色。

**实验 5：故意标定偏移（需要硬件）。**
把某个关节的零位故意偏 2 度，重新评估。
**观察什么：** 失败模式是什么样——是所有尝试都朝同一方向偏（系统偏差的特征），还是随机失败？这个实验让你以后能一眼认出标定问题。

**实验 6：移动相机（需要硬件）。**
采完数据、训好策略之后，把相机挪动 2 厘米或旋转 10 度，重新评估。
**观察什么：** 成功率掉多少。这个数字会让你以后认真固定相机。

**实验 7：改变光照（需要硬件）。**
在不同时间（早上、傍晚、开灯、关灯）各评估 20 次。
**观察什么：** 成功率的波动范围。这就是「换个时间跑就不成功了」这类玄学的量化版本。

**实验 8：跳过安全层（需要硬件，小心做）。**
把 `SafetyLimiter` 的限制放宽到很大（不是移除），观察策略输出里有多少动作原本会被拦住。
**观察什么：** 触发率。如果触发率很高，说明策略输出的动作幅度和你的限制不匹配，这时策略实际执行的是被削弱的版本——先解决这个再谈调参。

**实验 9：堵转观察（需要硬件，谨慎，控制在 10 秒内）。**
让机械臂轻轻顶住一个固定障碍物，监控电流和温度读数。**10 秒后立刻停止。**
**观察什么：** 电流上升到多少，多久开始发热。这个基线让你以后能设合理的过流阈值。不要做长时间堵转。

**实验 10：跳过 replay 的代价（需要硬件）。**
故意把采集的动作序列错位一帧存盘（模拟对齐 bug），然后跑 replay。
**观察什么：** replay 时能不能看出来「慢半拍」？如果能，说明 replay 这一步值得每次都做。

## 7. 与 Agent / 后端的类比

**SafetyLimiter = 权限门禁。** 在执行前检查边界、不信任上游输出、记录被拦下的请求。这就是 AgentTrust Runtime 在工具调用前做的事，代码结构几乎一样。

**分层调试 = 从底层往上排查依赖。** 数据库连不上就别怀疑业务逻辑。第 0 层到第 3 层的顺序和「网络 → 数据库 → 缓存 → 应用」是同一个思路。

**overrun 计数 = 延迟指标监控。** 一个每次都超预算的循环等于一个持续超 SLA 的服务，不能当成偶发警告忽略。

**三件一致性 = 训练服务一致性。** 阶段 05 讲过，这里是它在真机上的具体形态。

**replay = 数据管道的端到端测试。** 用真实数据走一遍完整链路，不经过模型。这就是集成测试跑在真实依赖上而不是全 mock 的价值。

**硬件档案 = 环境配置的版本记录。** 标定值、相机位置、光照条件就是这套系统的环境变量，不记录下来就无法复现。

## 8. 这个类比在哪里失效

**1. 没有回滚。** 后端的安全网是「出错了回滚」。这里没有：SafetyLimiter 能拦住一个还没执行的危险指令，但拦不住已经执行的动作的后果。所以它的设计原则必须是「宁可让任务失败」——因为失败可以接受，损坏不可以。这是防御性设计的强度差异，不只是程度差异。

**2. 环境不可复现。** 你的硬件档案再详细也复现不了今天的光照、今天的桌面摆放、今天你手的稳定程度。后端里 Docker 镜像加配置文件基本能复现环境。这里不能。这意味着「昨天能跑今天不能跑」是常态而不是 bug。

**3. 每台硬件都不一样。** 同型号的两台机械臂，标定值和噪声水平不同。「在我的机器上能跑」在这里不是笑话而是事实描述。你的策略在某种程度上是过拟合到这一台具体硬件的。

**4. 分层排查的层与层之间不是干净的接口。** 后端里数据库层和应用层有明确边界，你可以独立测试。这里第 1 层的标定误差会以「策略学得不好」的形式表现在第 3 层，症状完全在上层，原因完全在下层，中间没有边界能让你隔离。这也是为什么顺序不能颠倒——不是习惯问题，是层间无隔离的必然结果。

**5. 硬件会磨损。** 你的代码不会因为运行一万次而变差，舵机会。松动、磨损、发热老化都会让基线缓慢漂移。这意味着标定不是一次性任务，是需要定期重做的维护工作。软件工程里没有对应物。
