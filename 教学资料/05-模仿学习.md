预估投入 15-25 小时 · 需要 GPU · 产出：采集演示数据、训练 ACT 策略、诚实评估

## 这个阶段要解决什么

前四个阶段的技能层都是手写代码：IK 求解 + 轨迹插值。这个方法对刚性的方块抓取够用，但对以下情况会失效：

- 柔性物体（毛巾、线缆）——没有明确的「位姿」可求
- 需要接触反馈的任务（插拔、开抽屉）——纯位置控制会硬顶
- 难以用规则描述的动作（叠衣服、倒水）

模仿学习换一条路：**采集人类演示数据，让模型学出「看到什么就做什么」的映射。**

## 5.1 为什么是模仿学习而不是强化学习

两条路都能得到策略，选择逻辑：

| | 模仿学习（IL） | 强化学习（RL） |
|---|---|---|
| 需要什么 | 人类演示数据 | reward 函数 + 大量试错 |
| 真机可行性 | 高，几十条演示就能起步 | 低，需要几十万次交互 |
| 主要难点 | 数据质量、分布偏移 | reward 设计、sim2real |
| 失败模式 | 遇到没见过的状态就乱 | 学会作弊、钻空子 |
| 上手成本 | 低 | 高 |

真机操作任务几乎都用 IL，原因很简单：RL 要在真机上试错几十万次，机器人会先坏掉。RL 主要用在仿真里能大规模并行的场景（腿足 locomotion 是典型）。

**reward 设计有多难，值得你亲自体会一次。** 在阶段 01 之后如果你有兴趣，用 `stable-baselines3` 训一个「把方块推到目标点」的 RL 策略，你会看到它学出各种荒谬的作弊行为：把方块弹飞到目标点上方、卡在边缘反复抖动骗 reward、或者干脆学会不动（因为动了扣分更多）。

💡 联系你的经验：这和你给 LLM 写评测指标时遇到的问题一样——指标写得不严密，模型就会优化指标而不是优化你真正想要的东西。物理世界里这个现象更直观。

## 5.2 行为克隆及其根本缺陷

最朴素的模仿学习叫**行为克隆**（Behavior Cloning, BC）：把演示数据当成监督学习，输入观测，输出动作，最小化 MSE。

```python
"""最简单的行为克隆。

这个实现能跑，但会失败得很惨。理解它为什么失败，
比让它成功更重要。
"""

import torch
import torch.nn as nn


class SimpleBCPolicy(nn.Module):
    """单步行为克隆：观测 -> 动作。

    刻意写得很朴素，用来演示 BC 的失败模式。
    真实项目不要用这个结构。
    """

    def __init__(self, obs_dim: int, action_dim: int, hidden: int = 256):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(obs_dim, hidden),
            nn.ReLU(),
            nn.Linear(hidden, hidden),
            nn.ReLU(),
            nn.Linear(hidden, action_dim),
        )

    def forward(self, obs: torch.Tensor) -> torch.Tensor:
        return self.net(obs)
```

BC 有两个根本缺陷，它们不是实现问题，是方法本身的问题：

**缺陷一：复合误差（compounding error / 分布偏移）**

训练时模型看到的是专家轨迹上的状态。部署时模型自己开车，第一步有个小误差，就进入了一个训练数据里没出现过的状态，在这个状态下预测得更差，误差累积，很快完全跑偏。

这是 IL 最核心的理论问题，有个经典名字叫 **DAgger 问题**。缓解手段包括数据增强、加噪训练、以及让专家在模型犯错的状态下补充演示。

**缺陷二：多模态动作分布**

同一个观测下，人类演示可能有多种合理动作（绕左边走或绕右边走都行）。MSE 损失会让模型输出这些动作的平均值——而平均值往往是最糟的选择（正好撞上中间的障碍物）。

```
演示数据：有时向左 (-1)，有时向右 (+1)
MSE 最优解：0（正中间，撞墙）
```

这个缺陷是 ACT 和 Diffusion Policy 要解决的核心问题。

## 5.3 ACT：动作分块

ACT（Action Chunking with Transformers）来自 ALOHA 论文，是目前真机操作最常用的基线之一。

**核心思想一：动作分块（action chunking）。** 不预测单步动作，一次预测未来 k 步（典型 k=100）。

为什么这样有效：

- 减少复合误差的累积次数。执行 100 步只需要 1 次预测，而不是 100 次
- 隐式建模了动作的时序连贯性，避免抖动
- 缓解多模态问题——整段轨迹作为一个整体，不容易被平均成中间值

**核心思想二：时序集成（temporal ensembling）。** 每一步都重新预测一个 chunk，然后把多个 chunk 里对当前时刻的预测加权平均。这让动作更平滑，同时保留了高频反馈。

**核心思想三：CVAE 处理多模态。** ACT 用条件变分自编码器结构，训练时有一个编码器把演示动作压成隐变量 z，推理时从先验采样。这让模型能表达多种可能的动作，而不是被迫输出平均值。

```python
"""ACT 的核心结构示意。

这不是可运行的完整实现——直接用官方仓库或 LeRobot 的版本。
写在这里是为了让你理解它在做什么，读官方代码时不迷路。
"""

import torch
import torch.nn as nn


class ACTPolicySketch(nn.Module):
    """ACT 结构骨架。

    输入：多路相机图像 + 当前关节角度
    输出：未来 chunk_size 步的动作序列

    关键点是 forward 返回的是 (batch, chunk_size, action_dim)
    而不是 (batch, action_dim)。这一个维度的差别就是 ACT
    相对朴素 BC 的主要改进。
    """

    def __init__(
        self,
        action_dim: int,
        chunk_size: int = 100,
        hidden_dim: int = 512,
        num_cameras: int = 2,
    ):
        super().__init__()
        self.chunk_size = chunk_size
        self.action_dim = action_dim

        # 每路相机一个视觉骨干（通常是 ResNet18，ImageNet 预训练）
        # TODO: 实际实现里用 torchvision.models.resnet18
        self.vision_backbones = nn.ModuleList()

        # 关节角度投影
        self.joint_proj = nn.Linear(action_dim, hidden_dim)

        # Transformer 编码器-解码器
        self.transformer = nn.Transformer(
            d_model=hidden_dim,
            nhead=8,
            num_encoder_layers=4,
            num_decoder_layers=7,
            batch_first=True,
        )

        # chunk_size 个可学习的查询 token，每个负责预测一步动作
        self.action_queries = nn.Parameter(torch.zeros(chunk_size, hidden_dim))

        self.action_head = nn.Linear(hidden_dim, action_dim)

        # CVAE 的隐变量维度
        self.latent_dim = 32

    def forward(
        self,
        images: torch.Tensor,
        joint_positions: torch.Tensor,
    ) -> torch.Tensor:
```

## 5.4 Diffusion Policy

另一条主流路线。核心思想：把动作生成当成去噪过程。

从纯噪声开始，用一个网络反复去噪，最终得到一段动作序列。条件是当前观测。

相比 ACT 的优劣：

| | ACT | Diffusion Policy |
|---|---|---|
| 多模态表达 | CVAE，中等 | 天然强，扩散模型本就擅长多模态 |
| 推理速度 | 快，单次前向 | 慢，需要多步去噪（可用 DDIM 加速） |
| 训练稳定性 | 较好 | 较好 |
| 实现复杂度 | 中 | 中高 |

实践中两者性能接近，选哪个看具体任务和你的推理延迟预算。如果任务的多模态性很强（比如「把杯子放到桌上任意空位」），Diffusion Policy 通常更好。

**必读：** Diffusion Policy 论文（"Diffusion Policy: Visuomotor Policy Learning via Action Diffusion"）。

对你的建议：**先只做 ACT。** 两个都做会拖长这个阶段，而 ACT 的坑更少、社区支持更好。Diffusion Policy 留到你确定要深入的时候。

## 5.6 数据采集：这一步决定上限

模型质量的天花板由数据决定。这不是套话——同样的 ACT 实现，好数据和坏数据的成功率能差三倍。

**在仿真里采数据的两种方式：**

方式一，用脚本专家。你在阶段 02-03 写的 IK + 插值流程就是一个「专家」，让它跑 100 次，每次随机化物体初始位置，记录下观测和动作。这是最省事的做法，缺点是数据太完美——全是成功轨迹，且动作风格单一。

方式二，键盘/手柄遥操作。你自己操作机械臂完成任务。数据更像人类，但采集慢且累。

```python
"""从脚本专家采集演示数据。

关键设计点都写在注释里，每一条都是踩过的坑。
"""

from dataclasses import dataclass, field
from pathlib import Path

import numpy as np


@dataclass
class Episode:
    """一条演示轨迹。

    注意 actions 和 observations 的对齐关系：
    observations[t] 是执行 actions[t] 之前的观测。
    这个约定必须全程一致，错位一帧会让模型学出滞后的行为。
    """

    observations: list[dict[str, np.ndarray]] = field(default_factory=list)
    actions: list[np.ndarray] = field(default_factory=list)
    success: bool = False
    metadata: dict = field(default_factory=dict)

    def __len__(self) -> int:
        return len(self.actions)


def collect_episode(
    env,
    expert,
    max_steps: int = 400,
    randomize: bool = True,
) -> Episode:
    """采集一条演示轨迹。

    重要：即使失败的轨迹也要记录并保留 success 标记。
    很多人只保存成功轨迹，但失败数据在两个地方有用：
      1. 分析失败模式，改进专家或场景设计
      2. 某些算法（如带 reward 的 IL）可以利用负样本
    过滤在训练时做，不要在采集时做。
    """
    episode = Episode()
    obs = env.reset(randomize=randomize)

    for step in range(max_steps):
        action = expert.act(obs)
        if action is None:
            # 专家自己放弃了（比如 IK 无解）
            episode.metadata["abort_reason"] = "expert_gave_up"
            break

        # 先记录观测，再记录动作，保证对齐
        episode.observations.append(obs)
        episode.actions.append(action)

        obs, done, info = env.step(action)
        if done:
            episode.success = info.get("success", False)
            break

    episode.metadata["steps"] = len(episode)
    return episode
```

**数据采集的六个关键决定：**

**1. 初始状态随机化范围。** 太窄，模型只会一种情况；太宽，模型学不会。经验做法是从窄开始，训出能用的策略，再逐步扩大。

**2. 每条轨迹的长度一致性。** 差异太大会让训练不稳定。如果专家有时 100 步有时 400 步完成，说明专家本身不稳定，先修专家。

**3. 观测里放什么。** 至少要有图像和当前关节角度。**不要放物体真值位置**——模型会学会依赖它，而真机上没有。这是仿真训练最容易犯的错。

**4. 动作用什么表示。** 主要两种：绝对关节角度，或者相对当前的增量。绝对值更稳定，增量对初始位置变化泛化更好。ACT 通常用绝对关节角度。

**5. 控制频率。** 太高（比如 1000Hz）会让 chunk 覆盖的实际时间太短，模型学不到长程结构；太低（10Hz）动作会不平滑。真机常用 30-50Hz。

**6. 数据量。** 简单任务 50 条起步能看到效果，100-200 条能到可用水平。复杂任务需要几百到上千条。

## 5.7 训练与调参

ACT 的关键超参数，按重要性排序：

| 参数 | 典型值 | 影响 |
|---|---|---|
| `chunk_size` | 100 | 太小退化成 BC，太大末端动作不准 |
| 学习率 | 1e-5 ~ 1e-4 | 视觉骨干通常用更小的学习率 |
| batch size | 8 ~ 64 | 受显存限制，越大越稳 |
| 训练步数 | 50k ~ 200k | 看验证损失，但注意下一节的警告 |
| KL 权重（CVAE） | 10 ~ 100 | 太小退化成确定性策略 |
| 图像增强 | 随机裁剪、色彩抖动 | 对真机泛化很重要 |

**一个必须知道的坑：验证损失和实际成功率的相关性很弱。**

这是模仿学习里最反直觉的一点。你的验证 MSE 从 0.02 降到 0.01，成功率可能完全没变，甚至下降。原因：

- MSE 衡量的是「和专家动作的平均差异」，但成功与否取决于关键时刻的精度，不是平均精度
- 抓取的成败可能只取决于最后几帧的 3 毫米，而这几帧在整条轨迹的 MSE 里权重极小

**所以唯一可信的指标是在环境里实际跑的成功率。** 每隔一段训练步数就跑 20-50 次评估，记录成功率曲线。

💡 联系你的经验：这就是「代理指标 vs 真实指标」的问题，和做 LLM 工具评测时遇到的一样——单个工具的 E2E 成功率高，不代表端到端的问答质量好。这里的现象更极端。

## 5.8 诚实评估

这一节是本阶段最重要的部分，而且是工程习惯的直接延伸——在开发日志里区分本地、共享环境、生产三种验证证据的做法，在这里正好用得上。

具身领域的论文和 demo 视频普遍存在评估不严谨的问题。你从一开始就该建立正确的标准。

```python
"""策略评估：区分不同难度等级，记录失败模式。

这个类的设计目标是让「成功率 85%」这句话变得可核验：
在什么初始分布下、跑了多少次、失败的都是什么原因。
"""

from collections import Counter
from dataclasses import dataclass, field


@dataclass
class EvalConfig:
    """评估配置。

    必须显式声明初始状态的随机化范围，因为成功率对它极度敏感。
    「85% 成功率」在 5cm 随机范围和 20cm 随机范围下是两个完全
    不同的结论。不写清范围的成功率数字没有意义。
    """

    num_episodes: int = 50
    position_randomization: float = 0.05  # 米
    rotation_randomization: float = 0.0   # 弧度
    distractor_objects: int = 0           # 干扰物数量
    lighting_variation: bool = False
    seed: int = 0

    def describe(self) -> str:
        """人类可读的配置描述，必须和成功率一起报告。"""
        return (
            f"{self.num_episodes} 次, "
            f"位置随机 ±{self.position_randomization * 100:.0f}cm, "
            f"旋转随机 ±{np.rad2deg(self.rotation_randomization):.0f}°, "
            f"干扰物 {self.distractor_objects} 个, "
            f"光照变化 {'有' if self.lighting_variation else '无'}"
        )


@dataclass
class EvalResult:
    """评估结果，包含失败模式分布。

    只报告成功率是不够的。失败模式的分布告诉你下一步该改什么：
    大量 grasp_slip 说明抓取姿态或夹爪力度有问题；
    大量 wrong_object 说明视觉部分没学好；
    大量 timeout 说明策略卡住了，可能陷入了某种循环。
    """

    config: EvalConfig
    successes: int
    failure_modes: Counter = field(default_factory=Counter)
    episode_lengths: list[int] = field(default_factory=list)

    @property
    def success_rate(self) -> float:
        return self.successes / self.config.num_episodes

    def report(self) -> str:
        lines = [
            f"成功率: {self.success_rate:.1%} ({self.successes}/{self.config.num_episodes})",
            f"评估条件: {self.config.describe()}",
        ]
        if self.failure_modes:
            lines.append("失败模式分布:")
            for mode, count in self.failure_modes.most_common():
                lines.append(f"  {mode}: {count}")
        if self.episode_lengths:
            lines.append(
                f"平均步数: {np.mean(self.episode_lengths):.1f} "
                f"(最短 {min(self.episode_lengths)}, 最长 {max(self.episode_lengths)})"
            )
        return "\n".join(lines)
```

**评估纪律，五条：**

1. **报告成功率必须附带随机化范围。** 不写范围的数字没有意义。

2. **评估次数至少 50 次。** 20 次的置信区间太宽——成功率 60% 和 75% 在 20 次样本下无法区分。

3. **分等级评估。** 至少三档：训练分布内、轻度分布外（更大随机范围）、重度分布外（加干扰物或改光照）。三个数字一起报告，才能看出泛化能力。

4. **记录失败模式。** 光知道失败率没用，要知道怎么失败的。

5. **固定随机种子并记录。** 否则你无法复现，也无法比较两个 checkpoint 的优劣。

💡 这套纪律和严谨的后端工程实践是同一个东西：开发日志里区分本地、共享环境、生产三级验证，证据不足时拒绝声称完成。把这个习惯带进具身，你会比大部分同行更可信。

## 5.9 本阶段大作业

任务：在仿真里训出一个能抓方块的 ACT 策略。

步骤：

1. 用阶段 02-03 的 IK 流程做专家，采 100 条演示（位置随机化 ±5cm）
2. 观测里只放图像和关节角度，**不要放物体真值**
3. 用 LeRobot 训 ACT，或者自己接官方 ACT 实现
4. 训练过程中每 10k 步跑一次 50 次评估，画出成功率曲线
5. 分三档评估：±5cm（训练分布）、±10cm、±10cm 加 2 个干扰物
6. 统计失败模式分布，至少区分 4 种

**预期结果：** 训练分布内成功率 70-90%，±10cm 会明显下降，加干扰物会大幅下降。

如果你的 ±10cm 成功率和 ±5cm 差不多，检查一下是不是数据泄漏了（观测里混进了真值）。

**必做实验：**

1. **对比朴素 BC。** 用同一份数据训 5.2 节的 `SimpleBCPolicy`，对比成功率。你会看到 chunking 的价值。
2. **改 chunk_size。** 试 1、10、50、100，画出成功率对 chunk_size 的曲线。
3. **验证损失 vs 成功率。** 把两条曲线画在一张图上，观察它们的相关性有多弱。这个图值得你保留，它会改变你对「训练指标」的直觉。
4. **数据量消融。** 用 20、50、100 条数据分别训练，看成功率如何随数据量变化。
